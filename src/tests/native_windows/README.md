# Native Windows software tests

Configure this project with a native Windows compiler or an explicit Windows cross-toolchain. SQLite tests require `WSPRRYPI_SQLITE_ROOT`; journal, recovery, and pairing tests require both `WSPRRYPI_OPENSSL_ROOT` and `WSPRRYPI_BOTAN_ROOT`, including the matching OpenSSL SSL and crypto libraries. Omitted dependencies select an explicit subset. Cross-compilation does not execute any Windows test.

The optional `native_windows_restricted_runner` target supports software qualification from an elevated development session. Build it explicitly:

```powershell
cmake --build <build> --config Debug --target native_windows_restricted_runner
```

Create a fresh private test directory owned by the current account, with access limited to that account, SYSTEM, and Administrators. Copy the selected test executable and its matching runtime DLLs there. Invoke the launcher with the absolute directory and an executable basename from its closed software-test list:

```powershell
<build>\Debug\native_windows_restricted_runner.exe C:\private\test-run native_windows_file_test.exe
```

The launcher creates `probe-output.txt` exclusively, disables administrator membership and privileges in a same-user token, supplies a private default DACL, lowers integrity to medium, verifies the effective child token, and assigns a kill-on-close job before resuming execution. Its bounded child environment derives `SystemDrive` and the Windows directory from Windows APIs. A fresh directory is required for each attempt. The launcher returns the child result; errors, unsupported token operations, and timeouts are failures. It accepts no application or service command and performs no installation or account switching.

The allowed executable list excludes physical USB inventory/open tests. A passing software case does not qualify separate service SIDs, installed services, physical USB, power-loss durability, timing, or RF. Actual DLL/Python recovery tests additionally require the explicitly selected CPython 3.15 interpreter and matching recovery-age image documented in the recovery component.

The same launcher accepts only two additional closed modes for `native_windows_file_api_test.exe`: `python-binding` and `python-archive`. Supply the explicitly selected portable interpreter at `python/python.exe`, the checked-in Python modules and tests beneath `source/src`, and the matching recovery DLL beside the fixture. The archive mode also requires `recovery-age.exe` there. Hash-check all copied inputs before execution. These modes call the existing C++ fixture, which launches the selected interpreter under the reduced token; they do not accept arbitrary arguments or application commands.

`native_socket_test` exercises the actual WebSocket listener with an explicitly injected software backend session. It checks exclusive port ownership, noninherited handles, HTTP upgrade, text exchange, empty ping/pong, foreign-origin refusal, same-port restart after peer closure, shutdown during an incomplete handshake, and five immediate start/stop cycles. Local transmitter dispatch throws if reached. This fixture qualifies the transport boundary; production browser session authentication through the local backend requires its own integration test. The ordinary Make socket test remains the smaller socket-adapter subset.

The journal fixture exercises both production management journals and the listener cache, including complete file identity, private ACLs, cold replay, uncertain-operation fencing, replacement refusal, and a valid target history over one MiB. Native directory, SQL, and recovery publication ownership use distinct namespaces and require their separate interoperability tests. A shared reduced-token runner does not establish isolation between installed service accounts.

The journal image also exercises the production pairing catalog with synthetic records and the USB logging collector's existing no-device policy fixture. Catalog checks cover absent-history refusal, nonrecursive ownership, stale/invalid proposals, external replacement, publication faults, cold reopen, and a restored selector with its separate namespace and complete digest bindings. Logging checks cover persistence and restart, revision and source binding, unavailable journal enablement, and unsafe-state refusal. Neither fixture performs a pairing exchange or opens or inventories physical USB.

Release fixtures explicitly undefine `NDEBUG` so assertions remain active. MSVC reports command-line warning D9025 for that deliberate override; `/W4 /WX /permissive-` still applies to source compilation. Native library selections must match the compiler, architecture, and runtime of the fixtures; a cross-built Windows library is not interchangeable with an MSVC library.

`native_windows_pair_crypto_test` runs the existing production pairing test against the selected native libraries, including independent peers, exact transcript and key derivation, canonical encodings, terminal proof failures, and busy admission. It performs no discovery or network connection. `native_windows_maintenance_io_test` exercises protected passphrase FDs and encrypted export, then creates its own hidden child console for Unicode input and cancellation/restoration checks. It never attaches to an interactive-user console. `native_windows_maintenance_cli_build` compiles the actual command implementation separately; these boundaries do not qualify complete native recovery or separate service accounts.

`native_windows_manifest_test` verifies the process-local UTF-8 manifest through an actual Unicode path opened by the narrow standard-library interface. The manifest does not change system locale or code-page settings. `native_windows_dnssd_test` exercises the production native DNS-SD adapter through injected Windows API calls and actual SDK record allocation; it does not browse or publish on a real network.

`native_windows_service_owner_fixture` is an explicitly selected disposable-VM service fixture, excluded from ordinary builds, CTest, and the restricted same-user launcher. Its fixed `--provision` mode initializes the actual controller under its virtual service account. Its `--exercise` mode checks private-file denial, authenticated service identity, delayed reply delivery, changed-identity and wrong-PID refusal, the actual maintenance broker and its authenticated recovery channel, worker upload/cancel, encrypted backup, wrong-passphrase refusal, recovery preview, publication, and a changed boot/generation after restart under the distinct maintenance SID. A terminal capture-busy result may trigger at most eight fresh explicit backup requests within a bounded retry interval; every attempt is retained in the fixture evidence. Other backup errors are terminal. The `--web` mode runs the actual web process under its own service SID; the recovery exercise requires the configured HTTP and WebSocket listeners to be bound both before backup and after restart. The `--http-probe` mode checks the HTTP account’s private-file refusals without claiming a PHP/proxy runtime. The `--backend-probe` mode checks that the backend account cannot read maintenance, web, or HTTP private files, without initializing or changing backend identity/state. Provisioning and service operation require explicit authority for the four named test services and fixed private ProgramData/ProgramFiles roots. The fixture preserves existing identities, jobs, and failure evidence; compilation alone does not qualify these boundaries or complete recovery.

Validation retry requires a terminal failure and an exact private receipt bound to the current job and backend boot, with `busy` as its only error. Missing, malformed, or different receipts do not authorize retry. The bounded `--export-probe` mode independently drains the retained, unconfirmed failed restore's owner export without publishing state or exposing file contents; it checks the service PID, identity, nonce, response bounds, and complete transfer. A successful probe does not establish that the earlier interrupted exchange succeeded.

The fixed `--preview-probe` mode requires the latest retained restore to be failed, unconfirmed, and bound to the established controller. It reads the retained failed upload through a protected native handle, verifies its ciphertext size and SHA-256 against the saved job receipt, sends those exact bytes through a fresh production upload, verifies the returned archive digest, and requests preview using the synthetic fixture passphrase. Upload and validation each have a 240-second limit. It neither creates a backup nor confirms publication; a successful unconfirmed preview is cancelled through the production command before returning. A same-upload retry is permitted only for an exact job/boot-bound terminal busy receipt, with at most five validation attempts within the existing validation limit. This isolates source-owner admission and cleanup from backup creation. The fixture does not remove receipts, reset state, or treat an unresolved outcome as success. Disposable-host launchers must retain results and restore the exact controller executable and normal fixture service definition after a diagnostic run.

The full broker fixture opens a fresh authenticated recovery connection for each command, matching the one-request production CLI contract. Its smaller-chunk diagnostic uses 4,096-byte encrypted upload chunks and records that size in its evidence; it does not qualify the maximum chunk size. The independent native transport test sends the existing maximum 87,384-byte encoded chunk through the actual authenticated recovery channel. Neither test changes the production request limits or deadlines.

The fixed `--resume-probe` mode selects the active, already confirmed restore in `applying`, `awaiting_backend`, or a known failure other than `destination_changed`. With no active job, it admits only the latest job and requires that job to be a confirmed known failure. It starts the actual maintenance broker so the existing worker startup recovers that one durable job; a known failed job receives one explicit production `restore.resume` command. It then observes protected records for at most 240 seconds, allowing terminal registry cleanup to finish before teardown. It never resends confirmation, preparation, upload chunks, or a command with an unknown outcome. Only a verified `completed_held` result passes. A failure retains the confirmed job and holds for investigation; launching another full exercise does not substitute for recovering it.

The fixed `--backup-probe` mode uses the same actual broker, fixed service owners, normal controller startup, capture-busy receipt handling, and encrypted backup path as `--exercise`, then returns after the archive is ready. It skips the preliminary upload/cancel test and never uploads or confirms a restore. A passing backup probe does not qualify a complete recovery cycle.

The fixed `--retry-preview-probe` mode follows `--preview-probe` using the same retained ciphertext, but first requires terminal `archive_invalid` from a deliberately wrong synthetic passphrase. It then validates that same upload with the correct synthetic passphrase through the existing retry path. Preview remains unconfirmed and is cancelled on success. This tests retry separately from backup creation and the broker transport.

The separate-service-account recovery fixture retries backup/upload admission only after the exact closed `busy` reply, using the same request identifier and a 120-second test budget. It records these refusals separately from capture/validation attempts. Transport failure or an unknown outcome stops the fixture without replay. Production command deadlines remain unchanged.

The full recovery fixture polls job status once per second and records confirmation acknowledgment separately from completion polling. The resume probe observes protected records with a ten-second retry budget; every attempt repeats owner, ACL, full-identity, size, and strict-JSON admission, and no failed read authorizes an action. Persistent refusal fails the fixture. This is test observation behavior, not a production storage or command timeout.

`--quiesce-owner-probe` is restricted to the disposable fixture Maintenance service with no maintenance worker running. It authenticates the fixed Controller helper PID, SID, current schema, controller identity, helper mode, and nonce; requires a positive `root-available` reply from the serial owner; closes that connection; and stops only the same verified named helper service. Refusal or uncertainty prevents the stop. This allows an orderly code-unpin boundary for qualification diagnostics without interrupting an active owner operation or editing the retained job. It is not a product maintenance command.

The optional `WSPRRYPI_WINDOWS_CONTROLLER_RUNTIME_FIXTURES` CMake selection builds `pico_controller_pair_fixture` from the canonical zero-backend controller source inventory and `pico_tls_server`, a bounded raw software-peer relay frontend. Select the exact candidate source root, generated metadata directory containing both `build_metadata.hpp` and the verified `recovery_age_image.inc`, native dependency roots, and Python interpreter explicitly. These targets are excluded from ordinary builds and CTest. Controller objects use the established full-application `/W3 /WX /permissive- /utf-8` profile; fixture frontends use `/W4 /WX`. Missing provenance or generated inputs fail configuration.

The restricted launcher accepts `node.exe controller-network-pair` only for the fixed `source/WsprryPi-UI/tests/pico_controller_http_pair_test.js`, `peer-build`, and `pico_controller_pair_fixture.exe` paths beneath its private workspace. This mode has a ten-minute owned-job limit; previous modes retain their one-minute limit. Use a verified portable Node image and hash-check all source, credential, and executable inputs. This is a test dependency, not a product runtime requirement.

`peer_relay.py` runs only the explicitly selected actual Pico TLS/API/journal fixture on a POSIX qualification host. Its private session record authenticates three fixed software-peer argument lists; malformed, duplicate, unknown, and unauthorized requests are refused before launch. The Windows frontend transports raw control bytes through a task-owned loopback tunnel, while separate loopback forwards carry the actual TLS connections. The relay implements no Pico protocol responses and has bounded bytes, connections, child lifetime, and owned-process teardown. Record both executable hashes, exact source pair, relay/tunnel boundary, and final zero-owned-child result. This arrangement qualifies native Windows controller software against actual Pico software; it does not qualify native Pico execution on Windows, discovery, physical USB, installed hosting, or RF.

The controller pair fixture accepts the fixed `STOP` line on its Windows-only inherited stdin pipe, then invokes the existing application shutdown request. Its input poll is bounded, rejects other commands, and ends on pipe closure. The paired JavaScript test uses this private fixture channel for clean shutdown and restart; POSIX retains its existing signal path. Node’s Windows `SIGTERM` terminates a process and cannot establish a zero-exit graceful shutdown. This channel is absent from the product executable and adds no HTTP, CLI, or operator control.

`pico_management_usb_pair_client` reuses the existing independent and paired-controller USB fixture. On Windows its test-only stream forwards the same fragmented bytes to the actual explicitly selected Pico `usb_management_driver`, retaining production framing, ACK, context, journal, time-owner, and paired TLS negotiation. Select that actual build with `peer_relay.py --usb-build`; the relay verifies its image hash before every launch and serializes its owned USB children. The private inherited session record permits only that fixed USB executable with no arguments. Windows temporary fixture state is created with the current reduced-token owner and private ACL; no physical device is inventoried or opened. POSIX retains its existing owned pipe-child transport.

The restricted Node modes `controller-usb-pair` and `controller-usb-paired-pi` select only the checked-in USB management test, the workspace’s `pico_management_usb_pair_client.exe`, and `peer-build/peer-session.json`, with the fixed paired-mode flag when selected. Each mode has the same ten-minute owned-job bound as the network fixture. Use separate new private case directories to retain their individual output and input hashes.
