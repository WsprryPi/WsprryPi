# Step 1.2 — Define the comparison and evidence framework

## Status

Complete for documentary and methodology research. No mode recommendation, font selection, implementation, signal generation, hardware operation, or over-the-air test was performed.

## Technical summary

Later Hellschreiber research should use a **layered comparison record and mandatory evidence gates**, not a single weighted score. The framework must keep identity, logical encoding, sampled representation, waveform, RF transport, receive presentation, software support, observed use, and Wsprry Pi feasibility separate. Most apparent contradictions arise when values from different layers are compared as though they were the same quantity.

The framework has nine required dimensions: timing, raster, modulation, bandwidth, synchronization, font compatibility, software support, observed amateur use, and Wsprry Pi constraints. Each recorded value retains both the source's wording and a normalized interpretation. Unknown, conflicting, inferred, and not-applicable values are explicit states rather than blank cells.

The preliminary population is broader than fldigi's seven-mode menu. It includes standard and speed-scaled Feld-Hell, FSK/FM/MSK and PSK variants, Hell-80, Duplo, concurrent multi-tone C/MT, sequential multi-tone S/MT, and historical machine-specific systems. This inventory protects the schema from Feld-Hell-specific assumptions; Step 2 must still establish the authoritative taxonomy.

No defensible “most common for ham” conclusion is made here. Current sources illustrate the problem: fldigi documentation calls Feld-Hell most common, recurring North American material specifies FSK Hell-105, and the European net accepts FSK/FM Hell-105 or original Feld-Hell. These observations define the Step 4 measurement problem but do not resolve it. [HELL-EVID-0011] [HELL-EVID-0013] [HELL-EVID-0015]

## Research question

What fields, definitions, normalization rules, evidence standards, confidence grades, and decision gates will let later steps compare historical and amateur Hellschreiber modes fairly against standard Feld-Hell, current software, observed amateur practice, and Wsprry Pi constraints?

## Scope and non-goals

This step defines the research method and reusable comparison schema. It also performs a preliminary population check so the schema can represent known families.

It does not:

- finalize the mode taxonomy;
- select a preferred or production mode;
- determine the most common amateur mode;
- freeze a font or character repertoire;
- perform waveform, decoder, spectral, GPIO, hardware, or RF tests;
- design or implement Wsprry Pi changes;
- modify application code, submodules, UI, services, configuration, or operator documentation.

## Method and evidence base

The Step 1.1 baseline was treated as fixed. Current primary software documentation and source were used to test whether the schema can represent real variations. ADIF was examined as a logging vocabulary, not a waveform specification. Club schedules and results were used only to design adoption evidence fields. Wsprry Pi was inspected read-only at commit `0b0e539ce642bba89fc3d1fe87199772ee3a95aa` to identify confirmed architectural constraints and unknowns. [HELL-EVID-0011] through [HELL-EVID-0016]

This methodology-heavy report follows an answer-first technical structure: definitions precede comparison, evidence and limitations remain adjacent, and later decisions are gated by separately auditable dimensions.

## Canonical evidence states

Every field uses one of these states. Blank cells are prohibited when the state matters.

| State | Token | Meaning |
| --- | --- | --- |
| Observed | `OBS` | Directly stated or inspected in an identified source or measurement |
| Calculated | `CALC` | Reproducibly derived from observed inputs; formula recorded |
| Inferred | `INFER` | Best interpretation of indirect evidence; assumptions recorded |
| Conflicting | `CONFLICT` | Credible sources disagree or use irreconcilable definitions |
| Unknown | `UNKNOWN` | Sought but not established by adequate evidence |
| Not assessed | `NOT-ASSESSED` | Outside the current step or not yet researched |
| Not applicable | `N/A` | The concept does not apply; reason recorded |

Each material value also records source ID, access/version date, evidence independence, confidence, and any transformation used to normalize it.

## Timing comparisons preserve source and normalized values

### Required timing fields

| Field | Requirement | Normalization rule |
| --- | --- | --- |
| Source-stated rate and term | Required | Preserve verbatim numerical term such as “pixel rate” or “baud”; do not silently relabel |
| Character rate and duration | Required | Record char/s and seconds/character; state whether spaces are included |
| Logical-cell rate and duration | Required when raster-sequential | Count independently selectable states, not constrained duplicate samples |
| Column rate and duration | Required when column-scanned | Derive only when column structure and character timing are established |
| Elementary sample rate | Conditional | Record separately from baud when samples are constrained or oversampled |
| Inter-character/idle/leader timing | Required | Preserve blank time; distinguish cell spacing from message leader |
| Duty cycle | Conditional | State glyph/message/test-pattern basis; do not generalize a font average |
| Clock tolerance | Required | Separate transmitter accuracy, receiver acquisition range, and readable drift |
| WPM | Optional | Record the word convention; never use as the only timing value |

### Normalization formulas

For a fixed raster with `C` columns, `R` independently keyed logical cells per column, and character duration `Tchar`:

```text
column_rate       = C / Tchar
logical_baud      = C × R / Tchar
logical_cell_time = Tchar / (C × R)
```

If each logical cell is expanded into `D` constrained equal samples:

```text
elementary_sample_rate = logical_baud × D
elementary_sample_time = logical_cell_time / D
```

The expansion changes storage or sampled representation, not independent baud.

### Worked timing normalization

| Representation | Source/stored description | Normalized logical contract | Result |
| --- | --- | --- | --- |
| Feld-Hell direct | 7x7, 400 ms/character | `7 × 7 / 0.4` | 122.5 baud; 8.163 ms/cell |
| Feld-Hell paired | 7x14, 245 “pixels”/s | `14 samples ÷ 2 constrained samples/cell` | 122.5 baud; 245 samples/s; 4.082 ms/sample |
| Slow Hell in fldigi | 14 baud, about 0.28 char/s | Preserve 14 baud; verify its raster and exact rate in Step 2 before deriving more | `OBS: 14 baud`; other timing fields `NOT-ASSESSED` |

The Slow Hell row demonstrates the rule: a rounded typing rate and named baud are not enough to invent exact geometry.

## Raster comparisons separate four geometries

Every candidate must distinguish:

1. **glyph source geometry** — the stored bitmap or vector;
2. **logical signaling geometry** — independently selectable cells;
3. **transmitted sampled geometry** — duplicated, oversampled, or shaped samples;
4. **receive/display geometry** — repeated, interpolated, filtered, or cropped presentation.

Required fields are rows, columns, image-bearing area, blank spacing, duplicate constraints, traversal order, row/column orientation, leading/trailing blanks, and receiver repetition. A canonical diagram uses `c0…cN` left-to-right and `r0…rN` bottom-to-top; `1/#` is mark and `0/.` is space. If a source numbers in another direction, retain its numbering and record the transform.

Consequently, `5x7`, `7x7`, `7x14`, and “effective 5x10” are not comparable without their layer labels. A stored 5-column glyph may occupy a 7-column character cell; a 7-row logical glyph may be transmitted as 14 paired samples; a decoder may display more rows than were independently signaled.

## Modulation comparisons use four layers

| Layer | Required questions |
| --- | --- |
| Logical mapping | What raster state(s) are represented? Is there one binary state, multiple tones, phase states, or simultaneous rows? |
| Baseband/audio waveform | OOK/ASK, FSK/MSK, PSK, FM-derived, concurrent tones, sequential tones; tone count, spacing, polarity, phase continuity, and shaping |
| RF transport | Direct RF, SSB audio injection, AM/FM transport, sideband dependence, inversion behavior, and transmitter-linearity assumptions |
| Receiver interpretation | Envelope, frequency, phase, FFT row, polarity, tuning and sideband sensitivity, and human-versus-machine decision |

Record OOK, ASK, FSK, MSK, PSK, FM-derived, and multi-tone mechanisms precisely. “Hellschreiber” does not imply OOK. A software label such as FM Hell may describe a continuous-phase two-frequency method; the source's name and the measured mathematical classification must both be preserved until reconciled.

## Bandwidth comparisons require a declared metric

No bandwidth value is comparable until its definition is known.

| Bandwidth field | What must accompany it |
| --- | --- |
| Keying fundamental | Pattern, logical interval, and calculation |
| Null-to-null | Pulse shape and exact spectral null definition |
| Occupied bandwidth | Power percentage or other criterion, measurement point, duration, and test content |
| Width at attenuation | Reference level and attenuation, such as `-30 dB` |
| Necessary bandwidth | Regulatory/engineering definition and emission assumptions |
| Tone span | Lowest/highest tone centers and whether sidebands are included |
| Transmit filter width | Software/radio configuration, not relabeled as occupied bandwidth |
| Receiver filter width | Decoder recommendation and loss criterion |
| Waterfall/display width | Display settings and resolution; descriptive only |
| Sample rate | Never recorded in a bandwidth field |

A reproducible measurement additionally records sample rate, FFT size, window, overlap, observation duration, input level, test pattern/message, pulse shape, and measurement location.

### Worked conflict-preservation example

| Source claim | Original meaning | Normalized field | Treatment |
| --- | --- | --- | --- |
| 61.25 Hz | Alternating logical mark/space fundamental | Keying fundamental | `CALC`, not occupied bandwidth |
| About 200 Hz | Measured/argued containment for a shaped signal under stated conditions | Measurement with source-specific criterion | `OBS`; retain test conditions |

This is a reconciled set of different metrics, not five estimates of one number. [HELL-EVID-0005] [HELL-EVID-0008] [HELL-EVID-0010]

Before Wsprry Pi receives a spectral recommendation, an offline generator must be measured with a declared criterion across worst-case and representative glyph patterns, shaping choices, clock error, and each candidate output backend. Hardware/RF validation remains a separate authorization gate.

## Synchronization and framing are independent dimensions

Required fields include:

- continuous, burst, or framed stream;
- transmitter clock source and accuracy;
- receiver clock assumption and acquisition range;
- raster-phase synchronization;
- character framing, start/stop bits, preamble, leader, or sync pattern;
- blank, space, idle, and loss-of-signal behavior;
- resynchronization behavior and error propagation;
- receiver duplication or repeated display;
- visible effect of phase and clock error.

“No sync” must not mean “no timing requirement.” Standard Feld-Hell lacks transmitted raster phase and character framing but still requires a nominally matched raster rate.

Step 5 should test, where applicable: arbitrary acquisition phase, truncated leaders, blank characters, continuous and burst messages, modest positive/negative clock error, loss and reacquisition, and preservation of time during unkeyed cells. These tests are defined here, not executed.

## Font compatibility has four levels

| Level | Classification | Testable meaning |
| --- | --- | --- |
| F1 | Bit-exact | Same repertoire, logical matrix, cell ordering, spacing, and mark/space bitmap for every compared glyph |
| F2 | Raster/timing compatible | Same on-air raster contract and timing; one or more glyph bitmaps differ |
| F3 | Readable interoperability | Human-readable at the other endpoint, but repertoire, substitution, geometry, or decoder assumptions differ |
| F4 | Incompatible | Raster timing, traversal, modulation, or receive assumptions prevent dependable interpretation |

Each font record includes provenance, immutable file/revision, license, source/stored/logical/transmitted dimensions, stroke width, duplicates, case, digits, punctuation, space/control behavior, unsupported-character policy, transliteration, and checksum when frozen.

Human readability establishes at most F3 unless the bitmaps and timing are compared. Step 3 may freeze a reproducible reference only after the historical drum evidence and at least the common fldigi/G3PLX-derived and other actively used fonts are extracted, licensed, normalized, and compared character-by-character.

## Software support is versioned capability evidence

For each implementation, later research records:

- name, owner, version/revision, release date, maintenance status, OS/platform, and license;
- named Hell modes and aliases;
- transmit, receive, or display-only support separately;
- source availability and inspectable timing/font tables;
- configurable rate, raster, tone, shaping, inversion, filter, and font;
- logging identifiers such as ADIF and any mismatch;
- documented interoperability claims and verified interoperability evidence;
- installation accessibility and hardware assumptions;
- evidence access date.

`SUPPORTED-TX`, `SUPPORTED-RX`, `LISTED-ONLY`, and `VERIFIED-INTEROP` are distinct states. A menu item proves only that the version exposes a label. Current maintenance and historical influence are separate fields.

## Amateur adoption requires observations, not availability proxies

### Evidence hierarchy for Step 4

1. Time-bounded, mode-identified contact or spot records with deduplication and accessible raw counts.
2. Contest/sprint logs or results with entrant/contact counts and mode rules.
3. Recurring net check-ins or schedules with mode, frequency, date range, and participation records.
4. Representative receiver observations with recorded identification method.
5. Software telemetry or downloads only when the population and mode use are actually measured.
6. Surveys and expert statements with sample and question wording.
7. Operating guides, menu availability, search counts, and anecdotes as context only.

Every adoption observation records source, date range, geography, band, scheduled/routine context, mode-identification method, observations/stations/contacts, duplicate policy, selection bias, and confidence.

### Adoption labels

| Label | Minimum evidence rule |
| --- | --- |
| Dominant | More than half of a defined, representative Hell activity population, with uncertainty and denominator reported |
| Most common among observed activity | Largest share in at least two independent, time-bounded datasets covering materially different contexts; denominator and identification method reported |
| Commonly supported | Present with TX/RX support in multiple maintained implementations; makes no on-air claim |
| Historically influential | Strong historical documentation or long-lived implementation presence; makes no current-use claim |
| Niche but active | Recent, dated contacts, net participation, or multiple independent observations, but no representative dominance evidence |
| Insufficiently measured | Evidence lacks counts, independence, mode identification, or representative scope |

Software downloads, default settings, documentation volume, club membership, and search-result counts cannot alone establish on-air prevalence. If no representative dataset exists, Step 4 should publish a mixed-evidence conclusion with separate “supported,” “scheduled,” and “observed” findings rather than a fabricated market share.

### Why no adoption conclusion is made now

fldigi says Feld-Hell “seems to be” the most commonly used. Its operating wiki also documents a weekly FSK Hell-105 net. The European net defaults to FSK/FM Hell-105 or original Feld-Hell. Feld Hell Club sprint pages establish recurring activity but the accessible summary does not provide a complete mode-coded contact dataset. ADIF offers relevant submode vocabulary but cannot identify unlogged or ambiguously exported contacts. [HELL-EVID-0011] [HELL-EVID-0013] through [HELL-EVID-0015]

These are useful strata for Step 4, not sufficient data to assign “most common.”

## Wsprry Pi feasibility is a gated, backend-aware question

Read-only inspection confirms the following current contracts at the Step 1.2 source snapshot. [HELL-EVID-0016]

| Constraint area | Current state | Evidence state | Required later question |
| --- | --- | --- | --- |

| Language/build | C++20 parent application with Make-based build and multiple submodules | `OBS` | Can the implementation avoid an unsuitable dependency or license? |
| Existing modes | Configuration recognizes WSPR, QRSS, FSKCW, and DFCW; non-WSPR modes share message/base-frequency/timing concepts | `OBS` | Is Hell a distinct mode contract rather than an unsafe reuse of Morse timing fields? |

| Audio path | No general sound-card Hell output contract was established in this inspection | `UNKNOWN` | Would an audio backend be new scope, or should only existing RF backends be considered? |
| Resource budget | Build system is memory-aware, but no runtime Hell CPU/memory budget exists | `UNKNOWN` | Measure worst-case generation and scheduling jitter on the oldest supported target. |

### Mandatory feasibility dimensions

- timing determinism and jitter;
- backend ability to realize OOK, two-frequency, phase, or multi-tone events;
- frequency accuracy and PPM handling;
- pulse shaping and spectral containment;
- safe idle, cancellation, reload, shutdown, and GPIO lifecycle;
- deterministic offline rendering and envelope comparison;
- configuration compatibility and validation;
- scheduler/message duration and repeat-window policy;
- UI/CLI/web/persistence implications;
- CPU, memory, and platform range;
- font/software licensing;
- install/service privilege impact;
- later hardware and RF qualification.

Documentary feasibility is never hardware qualification. Multi-tone and phase-keyed candidates must not be rated feasible merely because the scheduler can emit single-frequency events.

## Compatibility and evaluation remain multidimensional

### Evaluation ratings

Each dimension receives `PASS`, `CONDITIONAL`, `FAIL`, or `UNKNOWN`, plus confidence and evidence IDs.

| Dimension | PASS requires | Hard failure or blocking unknown |
| --- | --- | --- |
| Historical fidelity | Identified primary/reconstruction evidence appropriate to the claim | Proven modern invention represented as historical |
| Feld-Hell interoperability | F1/F2 compatibility or demonstrated receive/transmit interoperation under defined conditions | Material timing/modulation incompatibility when Feld compatibility is claimed |
| Software interoperability | At least two versioned independent endpoints pass offline exchange | Menu/support claims only |
| Font reproducibility | Licensed immutable font, complete mapping, checksum, normalization | Missing glyph provenance or redistribution right |
| Amateur adoption | Meets a defined adoption label with denominators and bias | Unsupported “most common” claim |
| Timing feasibility | Deterministic offline events and bounded jitter across target range | Oldest claimed target unmeasured |
| Spectral feasibility | Declared metric passes offline worst-case measurements | Sample/filter values substituted for spectrum |
| Operational/RF safety | Safe idle/cancel/reload/shutdown and explicit transmit gating demonstrated | Any path can key hardware during offline tests |
| Maintainability | Fits architecture, tests, licensing, and supported platforms | Unmaintained opaque dependency is essential |

No total score is calculated. A high adoption rating cannot compensate for a safety failure; simple implementation cannot compensate for absent interoperability evidence.

### Mandatory recommendation gates

1. Step 1 baseline and comparison framework complete.
2. Step 2 authoritative taxonomy complete.
3. Step 3 reference and common fonts frozen with licensing.
4. Step 4 adoption assessed with denominators and limitations.
5. Step 5 offline interoperability and spectral tests pass.
6. Step 6 Wsprry Pi feasibility, safety, timing, resource, and configuration gates pass.
7. Step 7 recommendation explicitly separates documentary, offline, hardware, and RF evidence.
8. Any hardware or over-the-air validation is separately authorized and completed before a deployment claim.

## Confidence and conflict rules

- Repetition is not independence: copied tables count as one lineage until independent derivation is shown.
- Original specifications control historical behavior; current source controls a current version; neither silently controls the other.
- Software defaults are implementation evidence, not standards or adoption data.
- Calculations cite every observed input and formula.
- Negative searches establish only that a source was not found, not that a mode or feature does not exist.
- Stale software retains historical influence but cannot establish current maintainability.
- Conflicting values remain separate rows until definitions and conditions reconcile them.
- A source-dependent claim cannot gain “High” confidence from several mirrors of the same text.
- `UNKNOWN` is a valid outcome and a gate, not an invitation to fill from analogy.

## Limitations and robustness checks

- The candidate inventory was tested against fldigi, ADIF vocabulary, and a broad historical/software survey, but is not the authoritative taxonomy.
- Current club/net pages prove scheduled activity, not representative population shares.
- Software capability was sampled to validate the schema; DM780, MixW, IZ8BLY, mobile, web, and embedded implementations still need versioned enumeration.
- Wsprry Pi findings are source-level observations at one commit. No build, runtime, timing, audio, GPIO, or RF exercise was performed.
- The schema was checked against a direct sequential OOK mode, speed variants, two-frequency modes, concurrent/sequential multi-tone families, and incomplete historical evidence. This is sufficient to avoid a Feld-only schema but may require additive fields in Step 2.

## Decisions affected

- **HELL-DEC-0008:** Accept the layered canonical comparison schema and explicit evidence-state tokens.
- **HELL-DEC-0009:** Normalize logical baud separately from constrained sample rate and require declared bandwidth metrics.
- **HELL-DEC-0010:** Require quantitative or explicitly mixed evidence before using adoption labels; software availability is not on-air prevalence.
- **HELL-DEC-0011:** Use independent hard gates instead of a composite score.
- **HELL-DEC-0012:** Defer authoritative taxonomy, font, adoption, interoperability, and feasibility conclusions to their numbered steps.
