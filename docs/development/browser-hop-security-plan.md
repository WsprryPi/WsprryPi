# Browser-hop security implementation plan

Status: proposed; implementation has not started. The plan defines two browser modes for Pi and Pico for offline LAN operation. Preparing or approving this document does not install trust, change listeners, enroll devices, operate hardware, or authorize implementation, publication, commits, or pushes.

## 1. Outcome and scope

New Pi and Pico installations serve the operational dashboard over HTTP on port 80. Offer shack-CA HTTPS during first installation and as an optional upgrade at any later time. In HTTPS mode, authenticate the selected service before displaying secrets or enabling control, and protect the page, assets, API traffic, pairing codes, and WebSockets. Both modes preserve scheduling, target ownership, authorization, recovery, and machine-management contracts.

For HTTPS, use a small desktop enrollment tool on Linux, macOS, and Windows. It handles initial enrollment and browser trust after explicit operator consent, using a separately trusted bootstrap channel. Normal operation uses the existing UI in an ordinary browser. Enrollment does not install the controller application on the browsing computer and does not port #7's controller/runtime/services to Windows.

A shack that enables browser HTTPS uses one private certificate authority (CA). An HTTP-only installation can finish and operate without installing the desktop tool, creating an issuer, choosing a certificate namespace, or enrolling devices. A computer trusts the shack once per effective user/browser trust store. A newly enrolled device and every routine replacement certificate validate under that same trust anchor. Creation of a new shack is an explicit administrator action. Additional HTTPS servers enroll with the existing issuer. Additional HTTPS workstations trust the existing root once per effective store. Neither discovery nor an unavailable issuer creates a second CA.

Scope includes the existing Pi-hosted UI and direct Pico operator pages, their browser-facing APIs, pairing UI, retained commissioning/recovery entry points, and required enrollment/credential adapters. A browser managing a Pico through a Pi connects to the Pi under the Pi’s selected browser mode; existing authenticated Pi-to-Pico management remains a separate hop. Each directly browsed HTTPS Pico joins the shack once as a server. Every browsing computer already trusting that shack can open its admitted URL.

Non-goals: public Internet hosting, domain registration/ACME/cloud services, a general PKI, new user accounts/roles or single sign-on, new RF modes or scheduling, WTP restoration, replacement of machine pairing or Consumer-Radio encryption, the full #7 host port, a UI redesign, new firmware distribution infrastructure, or automatic mobile trust. No production change occurs during this planning task.

### Existing controller-to-device connections

The dashboard mode selects the connection from the browser to the host serving the page. The controller uses the following existing management connections in either dashboard mode.

| Controller and target | How control is authorized | Certificates the operator provisions |
| --- | --- | --- |
| Pi to paired Pi | Enter a temporary pairing code once. The Pis establish and rotate their own shared keys. Subsequent management connections automatically use TLS 1.3 with a pre-shared key. The target checks the current pair identity and the key’s permitted purpose. | None. No shack CA is required for paired Pi management. |
| Pi to consumer Pico over Wi-Fi (station or access point) | The Pi opens a Consumer-Radio session over HTTP/80 using the Pico password. The application authenticates and encrypts protected control messages. Some status is publicly readable on the LAN. | None. |
| Pi to engineering Pico on the station network | Mutual TLS authenticates the Pico server and the controller’s engineering client identity. | Engineering CA trust and provisioned server and client credentials. Browser approval of the shack root does not grant engineering client access. |
| Pi to Pico over USB | The dedicated physical management interface binds requests to the selected device and session. For a Pico attached to a paired Pi, the network leg uses paired Pi TLS and the final leg uses USB. | None on either leg. |

A failed paired TLS handshake refuses the connection. Sending the command over plain HTTP would lose the authenticated peer and purpose on which management authorization depends. Changing dashboard mode must neither change the selected device connection nor offer a plaintext retry. The Pico engineering field HTTPS password/cookie session is a separate profile with no corresponding Pi management client. See the [Pi TLS admission checks](../../src/wtp_integration/pi_pair_tls.cpp) and [Pi selection of Pico management connections](../../src/wtp_integration/pico_management_target.cpp).

## 3. Threat model and security claims

In HTTPS mode, address passive LAN interception, active page substitution, DNS/mDNS/address spoofing, TLS downgrade, wrong-device enrollment, proxy-header spoofing, mixed content, cross-origin requests/WebSocket hijacking, leaked enrollment material, stale trust, and interruption during credential publication. Discovery names and IP addresses locate a candidate; they do not establish identity.

Exclude compromise of the browsing OS, a malicious administrator, a compromised target, or a malicious trusted software-distribution channel from the protection claim. Preserve existing authorized-LAN and device-management policy: server-authenticated TLS does not authenticate a human, grant transmitter ownership, or revoke another user's LAN privileges. Do not describe a trust entry, cookie, or pairing code as a general login system.

A first HTTP visit, redirect, QR link, or JavaScript crypto exchange fetched through HTTP cannot establish trust by itself. On the HTTPS mode’s port 80 guidance page, never collect pairing codes, device passwords, backup passphrases, or private settings. A TLS error leaves controls unavailable; it must not trigger HTTP, direct-port, alternate-target, or alternate-carrier fallback. In HTTP mode, an on-path observer can read plaintext and an active intermediary can replace the page, capture secrets entered or displayed there, or change submitted controls. Pico Consumer-Radio encryption still protects its protocol messages but cannot authenticate the downloaded page code.

## 4. HTTPS desktop enrollment and browser qualification

Install the verified setup tool through the trusted distribution path. Offer **Trust this shack on this computer** once, showing the verified shack identity, root fingerprint, affected trust stores, effective scope, and how to remove trust. The setup tool performs the import with native consent and opens the dashboard in the intended browser. Ordinary visits and certificate renewals require no desktop helper.

For Pi HTTPS enrollment, use a local administrator invocation or an already authenticated SSH connection with verified host identity to a fixed, bounded enrollment command. Do not silently accept a new SSH host key or download the helper from the device's untrusted HTTP page. An SSH credential is operator authentication to an existing administrative channel, not a new Wsprry certificate-provisioning requirement. When no trusted administrator channel exists, stop and establish one explicitly; LAN discovery is not a substitute.

**Pi as the workstation.** On the Pi desktop, open the HTTP address supplied by installation directly in the ordinary browser. Use the local administrator command for optional mode readback or HTTPS setup. For HTTPS, first setup creates or joins the selected shack and enrolls this Pi as a server. Authenticate the public root against the shack administrator’s trusted record. Install it for the signed-in desktop user only if the effective store lacks the approved anchor. Open the admitted HTTPS address in the unprivileged browser. This requires no SSH, manual certificate import, or ongoing local renewal action.

**Second computer joining an existing Pi.** Open the supplied dashboard address or an existing bookmark directly, including on a computer visiting for the first time. An HTTP visit requires neither the helper nor an SSH account. If the operator wants authenticated readback of the Pi’s mode or help setting up HTTPS, offer **Connect to an existing Pi**. Let the operator pick the named Pi or enter its address, then read its identity, committed browser mode, and admitted LAN dashboard URL over verified SSH. This is a read-only operation on the Pi. Discovery locates candidates. A redirect, an open port, or a local bookmark cannot establish the Pi’s configuration. If the host identity is unverified, guide the operator to verify it at the Pi workstation before continuing. If the Pi has no committed mode yet, report that migration is pending and refer the operator to setup on the Pi. Do not guess a scheme or migrate the Pi from this flow.

Show the result in plain language, for example **Shack Pi uses HTTP** or **Shack Pi uses HTTPS**, together with the exact address. For HTTP, open the port 80 dashboard without changing browser trust. For HTTPS, read the shack identity and root fingerprint. If they match an approved root in this computer’s effective store, open the dashboard immediately. For first trust, obtain the public root and verify its fingerprint through the designated shack administrator channel in §4. Reuse the existing verified connection if the selected Pi is that authority. An SSH connection to an ordinary member proves only that member’s identity. A changed root requires the explicit recovery workflow in §7. Connecting this computer requires neither a transport choice nor a new device certificate. If this computer also hosts a controller, its own dashboard mode is a separate installation choice.

For initial direct Pico HTTPS enrollment, use the physically selected USB management role with operator-confirmed device/serial identity. Physical USB supplies local enrollment authority, not cryptographic proof against a malicious substituted USB device. Keep Console, reserved CDC, logging, and management/time roles distinct. The helper needs narrowly scoped native USB management discovery/serial adapters: Linux uses verified USB parent/interface identity, macOS its native device/interface metadata, and Windows SetupAPI/container/interface-role plus COM-port identity. Serial text or a matching VID/PID alone is insufficient. Do not reuse Linux sysfs/termios as supposed native Windows support, probe other CDC roles, install a custom driver, or silently fall back to a different transport. These helper adapters are not the full #7 controller port. Managing a Pico through either Pi browser mode uses the existing Pi-to-Pico authority. Use USB once per device enrollment to authorize the Pico’s membership for direct HTTPS, binding it to the selected shack and issuer. Any computer already trusting that shack can then browse it. A Pico-only deployment needs an identified LAN issuer host for this HTTPS design. Direct HTTP can operate without one.

Separate computer trust from device membership. Anchor a new computer through the shack administrator’s local or verified SSH channel, or independently verify the root fingerprint against that trusted source before import. An ordinary member device cannot authorize a new root for the computer. Over the trusted device bootstrap, exchange bounded, versioned enrollment records binding the shack, issuer endpoint and authenticated identity, device identity, authorized exact names/addresses, credential generation, nonce, and proof of possession. Keep private device keys on their owner. An issuing request from an enrolled device cannot change these bindings.

Qualify Windows 11 x64 with Edge and Chrome; macOS on Intel and Apple silicon with Safari, Chrome, and Firefox; Debian-family Linux amd64 with Chromium and Firefox; and Raspberry Pi OS Desktop on ARM with the Pi hosting Apache and running Chromium and Firefox locally. Record the Pi model, OS release, userspace architecture (arm64 or armhf), browser build, package source, and trust store for each promised ARM profile. Qualify each claimed architecture on a representative Pi desktop. Record exact supported OS/browser versions and packaging variants in the acceptance manifest before implementation. Windows ARM64 and other combinations remain unclaimed until separately qualified; Windows enrollment support does not imply controller-host support. For Linux, separately exercise browser profile/NSS and distribution packaging where applicable. For Windows, prefer per-user trust and verify the effective scope of a current-user CA trust entry. For macOS, constrain SSL trust to admitted service identities where supported and honor native authentication prompts.

Use genuine browser validation for the full chain. Prove that two distinct approved devices and a renewed leaf work after one trust installation. With only the intended root trusted, reject a chain from another shack. Test registry refusal of a request for a different member’s in-scope name independently from browser validation. In browsers, reject hostname mismatch, names or IPs outside the permitted subtrees, mixed permitted and forbidden SANs, a device-issued child, an expired leaf, and an out-of-scope certificate signed by the online issuer. Test every promised browser and name form. If constraints fail, hold the affected design for review before claiming support. Do not silently broaden trust, disable checks, or count a CLI probe as browser evidence.

Use owner-private per-user enrollment records under Linux `$XDG_STATE_HOME/wsprrypi/browser-trust` (or `~/.local/state/wsprrypi/browser-trust`), macOS `~/Library/Application Support/WsprryPi/BrowserTrust`, and Windows `%LOCALAPPDATA%\WsprryPi\BrowserTrust`. Resolve these through native user-directory APIs, not browser input; reject unsafe links or ownership and avoid roaming stores and stores shared across users. Record the verified shack identity, root fingerprint and generation, disclosed scope, actual trust store, browser profile, and owned entry identifiers. Where qualified browsers share an approved per-user entry, reuse it within the approved scope and verify the intended browser. A separate profile needs a new import only if its effective trust store lacks the entry. Change only tool-owned entries; preserve pre-existing trust and permissions. Recover interrupted installs/removals idempotently, report partial state, and verify native browser behavior before declaring enrollment complete. The helper need not remain running for browser use.

## 5. Shack CA, device certificates, and offline renewal

Designate one administrator-selected LAN host, normally the first Pi, to run an issuer service isolated from Apache, the browser backend, and maintenance clients. Generate a unique long-lived shack root and reserve offline root authority for issuer provisioning, handover, revocation, and root recovery. Routine device issuance uses only the constrained online intermediate. Retain the public root on clients. Keep the root private key off the operating issuer host after provisioning. The online issuer alone owns the intermediate key. Provision members with a root-authorized issuer service identity separate from device HTTPS certificates and the online signing key. Bind its role, endpoint, and generation in a verifiable handover record. Reserve the issuer name from device assignments. A member leaf, or any browser certificate minted by the online signer, cannot authorize an issuer replacement. Each device enrolled for direct HTTPS owns a unique non-CA TLS key and a separate purpose-bound renewal identity. Never reuse a machine-pairing, radio, backup, or signing key across these roles.

Assign stable device names within an explicitly chosen, locally resolvable shack namespace. Preserve existing names and exact IP URLs where they fit the qualified constraints. Preflight conflicts and explain any required bookmark or local name-resolution change before activation. Do not silently rename hosts, claim an unverified address, or authorize a whole LAN simply to accommodate DHCP. The issuer checks every SAN against the device registry, rejects duplicate assignments and wildcard requests, and produces server-authentication-only leaves. Devices changing identity or requesting additional names require separate administrator authorization.

Distinguish three limits. The registry controls what the running service agrees to sign. Issue the intermediate with critical DNS and IP name constraints and a zero path-length constraint. These limit what a stolen online signing key can issue to a compliant browser, within the qualified DNS and IP scope. An omitted name form can remain unconstrained. Qualify the actual permitted and excluded subtrees, including IPv4 and IPv6, before promising a DNS-only or address-limited scope. An ordinary browser authenticates the URL against its accepted roots. It cannot distinguish two trusted shacks issuing for the same name. Preflight overlapping namespaces and conflicting IP bookmarks before adding a second shack to a store. Require distinct qualified names or an isolated browser trust store where overlap would make identity ambiguous. The installed root itself can confer much broader TLS authority in its effective trust store, including through another intermediate signed by that root. Do not promise that an imported root is confined to the shack by the intermediate or by application policy. Disclose this residual authority before consent. Qualify excluded name forms and browser enforcement, and narrow the store scope where supported. A compromised online issuer can still impersonate devices within its allowed scope.

Each enrolled HTTPS device schedules its own LAN renewal before expiry with jitter and bounded retry. Authenticate the issuer independently of the expiring browser leaf. Authenticate the device using proof of its enrolled renewal key and current registry authorization. Generate the next server key locally, request only authorized SANs, validate the returned chain, key, device binding, names, and validity, then publish the key and complete serving chain atomically. Persist enough state to reconcile a lost reply or restart. Use a persistent request identifier to retrieve the same issuance result after a lost response. Verify activation against the actual TLS listener before discarding the previous valid key and chain. If activation fails, retain a coherent valid serving pair where possible and retry with backoff. Rate-limit retries and stagger fleet renewals. No Internet, browser visit, trust-store write, USB visit, or operator confirmation belongs in routine renewal.

Keep leaf lifetime and retry window open pending browser, device-resource, and outage validation. A 90-day lifetime and 30-day window are comparison cases only. Verify adequate overlap with issuer validity and realistic periods of device shutdown. The issuer and browsers need plausible local time without Internet NTP. For a cold start without reliable time, qualify a fresh nonce-bound time reply authenticated by the provisioned issuer service identity before validating certificate dates. Enforce persisted anti-rollback bounds and refuse implausible issuer time. If trusted time is unavailable, keep retrying the authenticated bootstrap. Show a clock-recovery action on the trusted administrator channel without requiring a working HTTPS dashboard. The issuer itself needs an independent trustworthy local clock or explicit administrator correction. Keep this observation within certificate handling and preserve RF time admission. Surface persistent renewal trouble and expiry with one recovery action. Compute warnings and retry deadlines from the earliest expiry in the usable chain. Alert the shack administrator once for an issuer-wide failure or approaching issuer expiry, and identify individual devices that still need attention after service returns. Healthy renewals produce no operator prompt.

Let the helper open the verified current URL; it need not edit browser bookmarks. Revoke browser sessions and target bindings on changes of origin, ownership, or security epoch. Ordinary same-origin leaf renewal under the same shack authority preserves valid session and pairing state, subject to existing disconnect and cleanup rules. A certificate failure or address change cannot replay a mutation or rearm output. TLS renewal/reload must preserve backend scheduling and existing cleanup; use graceful frontend replacement where the qualified runtime permits it. Session-owned transient tone/output still follows its existing disconnect cleanup. A TLS change does not promise to keep a transient command alive or resume it automatically.

After prolonged isolation, a browser rejects an expired leaf. Once the LAN issuer returns, a device with a still-authorized renewal identity and usable time can renew automatically even after leaf expiry. While a currently valid chain can still be served safely, an unavailable renewal channel pauses issuance only. If the chain expires, withhold browser control over HTTPS and keep the independent renewal client and trusted local recovery available. A retired device or unverifiable issuer cannot renew. Devices with no route to the issuer, including an isolated Pico AP, can serve only through the current certificate’s validity. No public DNS, cloud CA, Internet revocation lookup, or automatic HTTP fallback is required or permitted for recovery.

## 6. Browser mode selection and application integration

On a verified new Pi or Pico installation, commit `http-only` when setup completes with the default choice, including unattended setup. An explicit first-install HTTPS selection follows the staged activation below. Serve only the committed mode on the existing permitted interfaces and routes. For a verified legacy HTTP-only installation without a mode record, record that existing behavior and preserve its bookmarks. Reinstall and routine upgrades preserve any valid committed mode, including `https-required`. Where an older installation already serves HTTPS through custom configuration, preflight its existing access before migration. If the effective scheme, routes, or ownership cannot be determined safely, defer migration and preserve that configuration. A missing mode record is expected on the verified legacy installation during its first migration. Loss or corruption of a previously committed record, or inability to distinguish those cases, holds browser control for administrator recovery. Never interpret it as a fresh install. Change a committed mode through the Pi local administrator or verified SSH channel, or the physically selected Pico USB management interface. A browser request, imported settings, restore, or TLS failure cannot downgrade HTTPS.

In `http-only`, serve the operational UI and its assets, API, and existing browser controls at the device’s admitted HTTP origin on port 80 without desktop enrollment. This mode needs neither CA creation nor issuer availability. Changing the browser mode on a host that also runs the issuer leaves renewal service for other devices available. Pi proxies same-origin HTTP and WS through Apache. Pico serves its consumer routes directly on the interfaces admitted for the current station or AP profile and enforces its existing password and Consumer-Radio requirements. Keep the per-route limits, Host/Origin checks, CSRF defenses, machine authentication, device ownership, and transmitter safeguards in both modes. Mode selection grants no additional operation or interface.

Activate one operational browser mode at a time. Persist and activate changes recoverably, verify the resulting listener and mode through the administrator channel, and invalidate old sessions and pairing offers server-side and close old WebSockets before accepting new operations. Where the application uses session cookies, use distinct names for HTTP and HTTPS, retain HttpOnly and SameSite in both modes, and set Secure on HTTPS cookies. Accept only sessions issued for the active mode, origin, and activation, even if the browser retains or sends an old cookie. In HTTP mode, suppress browser-certificate maintenance prompts. On an explicit return to HTTPS, reuse current membership and automatically renew an expired leaf before cutover. If preflight fails, retain the committed HTTP mode and report the cause. After HTTPS commits, a failure cannot reopen HTTP. Account for cached HSTS on an enrolled hostname before switching to HTTP, including browsers offline during the switch. Where possible, expire WsprryPi’s own cached policy over verified HTTPS for the initiating browser before cutover. Other computers need not be online to approve the change. A browser that misses the update may continue upgrading the hostname until its own cached policy expires. Keep the trusted administrator channel available throughout. An interrupted transition must recover to the committed mode or hold for local recovery.

On Pi, preflight every Apache virtual host serving the application, including existing custom HTTPS sites. Limit changes to WsprryPi routes and credentials. If enforcing the selected mode would replace a shared certificate or affect other applications, report the exact conflict and leave the current installation in place until the administrator resolves it. Terminate browser TLS in Apache using the existing same-origin application paths and proxy model. Allow TLS 1.3; do not add TLS 1.2 merely to support an unqualified browser. Only the credential owner and narrow TLS terminator may read the private leaf key. On Linux use a root-owned `0700` `/var/lib/wsprrypi/browser-tls` owner directory and `0600` private-key files, outside the web root and backend SQLite generation tree; Apache obtains the key through its admitted master/credential-loading lifecycle, not a world-readable copy. Reuse the existing bounded privileged maintenance lifecycle for typed prepare/activate/recover operations rather than creating a generic privileged daemon. The unprivileged browser/backend receives public metadata and typed results only. Pico needs an identity-bound, recoverable credential record in its existing provisioning/flash ownership model, with erase/transfer behavior, no source-tree/image key, and firmware-size/memory validation before activation. Keep the backend, browser runtime, and maintenance identities separate and preserve current network admission. Internal loopback/verified IPC traffic is a separate boundary; it must not become remotely reachable to bypass TLS.

In HTTPS mode, serve the page, scripts/styles/fonts, API, pairing display/submission, events, downloads/uploads, and WebSockets from the admitted HTTPS origin. Audit the complete route inventory, including Maintenance, support bundles, recovery, configuration, and auxiliary PHP endpoints. In either mode, report proxy failures and keep browser traffic off direct backend ports 31415/31416. Require WSS under HTTPS and reject cross-origin, null/malformed/duplicate authorities and untrusted forwarded metadata before mutation. Preserve exact Host/Origin/proxy/CSRF, body-size, rate, unknown-response, and request-id rules.

On Pi, use the transport context authenticated by the Apache proxy/IPC boundary to establish scheme; never trust a client-supplied forwarding header or Origin as proof of TLS. Set Secure/HttpOnly/SameSite session cookies for secure browser use, bind them to the admitted origin/context, and retire them on trust/authority epoch transitions. WebSocket upgrades must receive the same authorization intended for the existing browser command lane; adding encryption must not bypass backend revalidation or release/cleanup semantics.

For direct Pico pages, add the necessary consumer HTTPS admission and public TLS material/provisioning resource without conflating engineering mTLS and ordinary browser authentication. Preserve existing password/Consumer-Radio protections inside the authenticated page, profile/journal/delivery rules, memory limits, time management, and response acknowledgments. On Pico, derive transport from the accepted connection and match the exact browser origin and port for the selected mode. Preserve the existing Consumer-Radio exchange on LAN HTTP without treating that origin as a secure context. Inventory exact carrier/interface/port/method/resource admission rather than recognizing clients by User-Agent or broadening scheme allowlists. Transport provenance must establish whether the browser crossed TLS; a machine request must still satisfy its independent existing authority. Engineering HTTPS/mTLS, native Pi paired TLS, USB, and non-browser machine Consumer-Radio traffic retain their distinct authority and keys.

A new Pico serves HTTP on its existing permitted station or AP routes once that interface is available. Ordinary HTTP browser access requires no USB mode selection. Offer direct HTTPS enrollment during first provisioning or later through the selected USB management interface. Starting an AP respects the committed mode and its route limits. Independent BLE and USB provisioning retain their own admission rules.

In both modes on Pi, bind internal HTTP/WebSocket listeners to loopback or an equivalently restricted local endpoint and restrict access to the admitted Apache proxy path. Close the UI’s direct-port fallback. The backend must consume only verified proxy/IPC transport context, with the proxy stripping caller-supplied transport-identity and forwarded-scheme headers and supplying its own admitted identity. A claimed HTTPS Origin, X-Forwarded-Proto, network address, or cookie flag alone cannot authorize secure-browser traffic. Test direct LAN access to ports 31415/31416 and duplicate/spoofed proxy headers. Preserve separately registered machine/bootstrap/Consumer-Radio carriers with their existing cryptographic admission; an encrypted machine endpoint is not permission to serve the operational browser page over HTTP.

In HTTPS mode on either device, browser routes on port 80 may provide a bounded non-secret recovery/help page and a redirect to a configured verified HTTPS authority. Never derive that authority from untrusted discovery or arbitrary Host input. It cannot display/accept pairing codes, passwords, backup passphrases, private settings, control requests or browser WebSockets. Its page remains unauthenticated, so do not download or run enrollment software from it, treat its instructions as proof of device identity, or use it to weaken OS trust. Apply help and redirects only to browser guidance routes. Separately registered machine requests sharing a listener still go to their existing handlers under their own admission rules. Certificate, proxy, and enrollment failures never enable operational HTTP.

Audit mixed content and third-party runtime assets. Bundle assets necessary for offline operation where already legally distributable; in HTTPS mode block active HTTP content and remove insecure endpoint fallback. Introduce response hardening, no-store for secrets, and a CSP through tested report-only observation followed by enforcement compatible with existing UI code; keep any violation observation local and redact URLs/payloads rather than introducing telemetry; do not rewrite unrelated frontend architecture. Stage HSTS after testing HTTPS recovery on a dedicated hostname whose policy the device owns and whose qualified browser profile supports it. Start at 300 seconds with no preload or includeSubDomains. Do not rely on HSTS for first contact, IP origins, transport authorization or downgrade prevention; a stale policy must not strand local recovery.

### Operator FAQ for first use

Include these questions in the operator connection guide when the feature ships, and make them available from the optional HTTPS setup offer.

**Do I need HTTPS if my station is only on my LAN?** HTTP on port 80 is a reasonable choice on a private, isolated shack network where you control the connected equipment and are comfortable trusting the network. You can use it without setting up certificates. A LAN can be closed to the internet and still have shared computers or a compromised router. HTTPS lets your browser verify the station at its address and protects the dashboard, pairing codes, and commands from being read or changed in transit. That protection is particularly useful on a shared home or club network. You can enable it later.

**Could someone take over my Pi or Pico?** Someone able to intercept an HTTP connection could change the page you see, capture a pairing code, or alter a settings or scheduling request. That can affect station operation without giving the person a login on the Pi or control of the Pico firmware. Taking over the device itself would require separate access, such as stolen administrator credentials or an exploitable flaw. HTTPS protects the browser connection. It does not decide who may operate the station or repair an already compromised computer or device.

**If my dashboard uses HTTP, do I need certificates to control another Pi or Pico?** Pair two Pis by entering the pairing code. They use their own shared key to recognize each other and protect commands. TLS stays on automatically because the receiving Pi uses that connection to verify which controller is sending the command. There are no Pi pairing certificates to install or renew.

For a consumer Pico, use its password over Wi-Fi or connect its management USB cable. Neither option needs a certificate. Over Wi-Fi, the Pico and controller protect control messages even though they travel over HTTP. The engineering station profile uses certificates on both devices. If you later enable HTTPS on your dashboard, your existing control connections keep using the same credentials.

## 7. Pairing, ownership transfer, restore, and recovery

The existing Pi management-pairing protocol and purpose keys stay unchanged. The target displays the code and the manager accepts it only through their respective admitted operational origins. Each device enforces its own mode. A pairing workflow has browser-hop protection end to end only when both browser visits use verified HTTPS. Device pairing and issuer enrollment are separate actions. Opening an already enrolled peer under a trusted shack needs no further browser trust approval. Keep current code expiry, attempt limits, originating view/boot/device binding, cancellation, and uncertain-operation reconciliation. Never display or transport the code in URLs, discovery, logs, support bundles, analytics, shell arguments, or persisted browser storage.

Server TLS identity, machine pair authority, desktop trust entries, and browser sessions are separate records. Unpairing a machine does not automatically erase browser trust or revoke an authorized LAN user's access. This plan does not add user/client certificates or account roles; any requirement to revoke particular human browsers is a separate authorization decision, not a claimed effect of server TLS.

On device retirement or ownership transfer, retire local sessions and offers. If the device has ever been enrolled, including a former HTTPS device now using HTTP, disable its renewal authorization and erase its browser and renewal secrets. For that enrollment, confirm issuer-side retirement or report it pending if the issuer is unreachable. A device that has never been enrolled has no CA retirement step. Enroll the new owner’s device with fresh keys and the intended shack before serving HTTPS. A verified fresh installation for the new owner follows the HTTP default. For an in-place ownership transfer, keep the existing transfer hold until the new owner confirms the intended access. This confirmation can be part of accepting the transfer. Other members retain their shack trust. Blocking future issuance cannot instantly invalidate an already issued certificate on an offline browser. Document the exposure until expiry and the supported local distrust procedures.

Preserve valid destination identity, mode, and credentials across reinstall or settings-only restore. For credential-bearing recovery of an enrolled device, retire its old renewal binding. Generate fresh browser and renewal keys and authorize the destination before serving HTTPS again. A destination using HTTP can defer fresh enrollment until HTTPS is requested. A never-enrolled device can restore ordinary HTTP service after existing recovery holds clear, with no issuer contact. Same-shack browsers keep their existing root. A move cannot activate another device’s keys or restore its sessions. Exclude CA secrets, device private keys, renewal identities, and desktop trust records from ordinary application backups and diagnostics. Preserve restore holds and defer HTTPS provisioning when the administrator has selected HTTP. If a transfer or reinstall would erase signer data or move the issuer service, complete the issuer handover before that operation. An in-place reinstall preserving the verified issuer state needs no handover. A routine application restore must never roll back the issuer registry.

### Issuer backup, replacement, and compromise

At shack creation, provide an encrypted, administrator-controlled offline recovery package for the root key and chain, with independent custody of the unlock secret. Back up the enrollment and issuance journal separately, including approved bindings, restrictions, retirement and revocation state, issuer generations, and signed policy. Verify recovery off the original host before relying on it. Have the issuer maintain a separately authenticated, independently stored current checkpoint of registry changes. Compare restored generation and journal continuity against it before resuming signing. If freshness cannot be established, treat all affected memberships as uncertain, including those listed as active in a valid but older backup. Where current authorization cannot be established, hold issuance for the uncertain entries until reconciled through trusted enrollment.

For loss of an issuer host without suspected compromise, fence the old host, restore the verified registry on a replacement, use the offline root to certify a fresh constrained intermediate, and publish the replacement at the authenticated LAN endpoint. Devices verify the issuer role, shack identity, and replacement chain under their provisioned root. Exercise address changes through a trusted handover. Resume queued renewals automatically. Browsers retain the same root. For ordinary rollover, start serving the new intermediate with new leaves while devices with valid old chains continue using their bundled intermediate. Test the issuer host renewing its own dashboard with Apache unavailable. For replacement, require a root-authorized handover to the new service identity and a single active writer. Persist the highest authenticated issuer generation and reject rollback. An isolated device cannot learn about a compromise until it receives trustworthy updated state. If the handover cannot be verified automatically, identify the affected device for trusted local recovery. Retain a verifiable handover path for devices that missed several generations. If current registry evidence is missing, restore service only for memberships whose authorization can be independently reconciled. If the former signer cannot be accounted for or fenced, use the compromise procedure.

For a stolen intermediate, isolate the signer, revoke it, publish local status, and replace it under the offline root. An offline browser or one that ignores private revocation information can still accept the old chain until expiry or effective local distrust. Do not report universal revocation from database state. After signer compromise, reissue every affected device leaf with the replacement intermediate, serve the new chains, and verify renewal clients reject the retired issuer service authority. If the issuer host or registry integrity is in doubt, reconcile device authorizations from independent evidence before resuming. For root compromise, abandon the old authority, create a distinct shack root, explicitly distribute it over independently verified channels outside the compromised trust path, rebind devices, remove or distrust the old root on each affected store, and track unavailable computers. Root loss without a usable backup likewise requires a planned trust migration before the surviving issuer expires. Schedule normal root rollover with overlap and explicit trust approval well before expiry. Loss of an issuer, root, or backup never enables operational HTTP.

## 8. Mobile boundary

Desktop qualification covers both modes. Mobile HTTP requires no CA enrollment. Mobile HTTPS requires a separately qualified, operator-approved trust workflow for the same shack root. A desktop’s approval cannot enroll a phone.

Qualify mobile trust scope and removal on real devices before advertising mobile HTTPS. Responsive viewport testing covers layout only. No mobile trust installation or managed-device deployment is implicit in desktop setup.

Broader CA trust, mobile support and #7's host port are not implicitly authorized. No deployment, trust-store mutation on the user's computers, services, firmware installation or RF exercise is authorized by this document.

## 11. Assessment loop and remaining decisions

Assess the entire plan/implementation against the threat model, route inventory, source pair, package/trust lifecycle, user workflow and acceptance matrix. Fix actionable in-scope findings, rerun affected checks, then perform another full assessment including retained paths and recovery. Repeat until a full pass finds no further actionable finding. Reopen affected evidence after subsequent edits. Missing qualification is a named gate, never a clean assessment or broad readiness claim.

The selected design uses HTTP on port 80 by default and optional shack-CA HTTPS with automatic LAN renewal. Outstanding gates include the browser constraint matrix, offline root custody, local name and time availability, exact issuer host and storage requirements, Pico capacity, retirement and recovery evidence, and measured validity and outage windows. A failed gate requires an explicit design decision. Cross-repository edits, disposable-host execution, package signing, and deployment retain their separate authorization boundaries.

Completion requires implementation and documentation of both browser modes, passed exact-source integration and qualified desktop trust/profile tests, demonstrated recovery, and an accurate report of remaining physical/deployment limits. This plan alone completes none of those implementation gates.
