# Browser-hop security implementation plan

Status: proposed; implementation has not started. The selected UX is desktop enrollment with offline LAN operation. Preparing or approving this document does not install trust, change listeners, enroll devices, operate hardware, or authorize implementation, publication, commits, or pushes.

## 1. Outcome and scope

Protect the page and assets delivered to the operator, API requests/responses, WebSocket upgrades/messages, and the display/submission of pairing codes. The browser must authenticate the selected service before displaying secrets or enabling control. Preserve existing scheduling, target ownership, authorization, recovery, and machine-management contracts.

Use a small desktop enrollment tool on Linux, macOS, and Windows. It automatically handles certificates and browser trust after explicit operator consent, using a separately trusted bootstrap channel. Normal operation uses the existing UI in an ordinary browser. Enrollment does not install the controller application on the browsing computer and does not port #7's controller/runtime/services to Windows.

Prefer explicit trust of the selected non-CA server certificate. A broadly trusted private CA is not approved. Browser compatibility is a feasibility gate, not an assumed property: if direct leaf trust cannot meet the selected browser profile without disabling validation, stop for a focused decision. Do not silently substitute a CA, an extension, a mobile app, a certificate-warning bypass, a new browser, or public DNS infrastructure.

Scope includes the existing Pi-hosted UI and direct Pico operator pages, their browser-facing APIs, pairing UI, retained commissioning/recovery entry points, and required enrollment/credential adapters. A browser managing a Pico through a Pi authenticates the Pi's browser origin; existing authenticated Pi-to-Pico management remains a separate hop. Direct Pico browsing needs its own enrollment.

Non-goals: public Internet hosting, domain registration/ACME/cloud services, a general PKI, new user accounts/roles or single sign-on, new RF modes or scheduling, WTP restoration, replacement of machine pairing or Consumer-Radio encryption, the full #7 host port, a UI redesign, new firmware distribution infrastructure, or automatic mobile trust. No production change occurs during this planning task.

## 3. Threat model and security claims

Address passive LAN interception, active page substitution, DNS/mDNS/address spoofing, TLS downgrade, wrong-device enrollment, proxy-header spoofing, mixed content, cross-origin requests/WebSocket hijacking, leaked enrollment material, stale trust, and interruption during credential publication. Discovery names and IP addresses locate a candidate; they do not establish identity.

Exclude compromise of the browsing OS, a malicious administrator, a compromised target, or a malicious trusted software-distribution channel from the protection claim. Preserve existing authorized-LAN and device-management policy: server-authenticated TLS does not authenticate a human, grant transmitter ownership, or revoke another user's LAN privileges. Do not describe a trust entry, cookie, or pairing code as a general login system.

A first HTTP visit, redirect, QR link, or JavaScript crypto exchange fetched through HTTP cannot establish trust by itself. Never collect pairing codes, device passwords, backup passphrases, or private settings on that page. A TLS error leaves controls unavailable; it must not trigger HTTP, direct-port, alternate-target, or alternate-carrier fallback.

## 4. Desktop enrollment and browser qualification

The operator installs a verified enrollment package from the existing trusted distribution path, selects a device, authenticates the bootstrap channel, reviews the device identity and proposed names/addresses, approves the exact browser/profile trust changes, and opens the verified HTTPS URL. There is no manual certificate creation, private-key copying, or editing of trust-store files. Authentication prompts and explicit trust consent are intentional.

For Pi first enrollment, use a local administrator invocation or an already authenticated SSH connection with verified host identity to a fixed, bounded enrollment command. Do not silently accept a new SSH host key or download the helper from the device's untrusted HTTP page. An SSH credential is operator authentication to an existing administrative channel, not a new Wsprry certificate-provisioning requirement. When no trusted administrator channel exists, stop and establish one explicitly; LAN discovery is not a substitute.

For a directly browsed Pico, use the physically selected USB management role with operator-confirmed device/serial identity. Physical USB supplies local enrollment authority, not cryptographic proof against a malicious substituted USB device. Keep Console, reserved CDC, logging, and management/time roles distinct. The helper needs narrowly scoped native USB management discovery/serial adapters: Linux uses verified USB parent/interface identity, macOS its native device/interface metadata, and Windows SetupAPI/container/interface-role plus COM-port identity. Serial text or a matching VID/PID alone is insufficient. Do not reuse Linux sysfs/termios as supposed native Windows support, probe other CDC roles, install a custom driver, or silently fall back to a different transport. These helper adapters are not the full #7 controller port. Do not require USB enrollment merely to manage a Pico behind an already authenticated Pi UI.

Define one closed, size-bounded enrollment document binding device/installation identity, current credential epoch, challenge nonce, leaf certificate/public-key digest, exact SAN authorities, supported browser URL, and transport context. The tool verifies proof of possession and binding inside the trusted bootstrap exchange before modifying trust. It never accepts an arbitrary downloaded certificate, browser-supplied store path, wildcard authority, or caller-selected private-key destination. The bootstrap exchanges public certificate/CSR material only; server private keys remain with their device owner.

Qualify Windows 11 x64 with Edge and Chrome; macOS on Intel and Apple silicon with Safari, Chrome, and Firefox; and Debian-family Linux amd64 with Chromium and Firefox. Record exact supported OS/browser versions and packaging variants in the acceptance manifest before implementation. Windows ARM64 and other combinations remain unclaimed until separately qualified; Windows enrollment support does not imply controller-host support. For Linux, separately exercise browser profile/NSS and distribution packaging where applicable. For Windows, prefer per-user trust and distinguish Trusted People/leaf semantics from Trusted Root CA trust. For macOS, constrain SSL trust to admitted service identities where supported and honor native authentication prompts.

The feasibility test must use genuine browser validation with `CA:FALSE`, server-authentication usage, exact SAN matching, appropriate key usage, valid dates, and refusal of a different certificate/device. Also prove the installed entry cannot validate an attacker-issued child certificate or an unrelated hostname. Do not equate importing a file, a successful CLI TLS request, or disabled browser errors with success. An unsupported browser/profile is a visible refusal, not silent exclusion from the agreed matrix.

Use owner-private per-user enrollment records under Linux `$XDG_STATE_HOME/wsprrypi/browser-trust` (or `~/.local/state/wsprrypi/browser-trust`), macOS `~/Library/Application Support/WsprryPi/BrowserTrust`, and Windows `%LOCALAPPDATA%\WsprryPi\BrowserTrust`. Resolve these through native user-directory APIs, not browser input; reject unsafe links/ownership and avoid roaming or shared key stores. Maintain: exact device identity, authorized authorities, credential epoch/digest, store/profile and owned entry identifiers. Change only tool-owned entries; preserve pre-existing trust and permissions. Recover interrupted installs/removals idempotently, report partial state, and verify native browser behavior before declaring enrollment complete. The helper need not remain running for browser use.

## 5. Device certificates, names, renewal, and offline operation

Generate a unique P-256 server key with a qualified device CSPRNG and a non-CA server certificate. Never derive it from a management, retirement, PAKE, Wi-Fi, backup, or other purpose key. The target owns the private key; the desktop receives only public material. No CA signing service or shared factory certificate is introduced.

Use existing explicit hostnames and verified current addresses, including IPv4/IPv6 only where actually supported, as exact SAN entries and admitted origins. Preserve custom hostnames and machine identities. Do not claim `.local` resolution works on every Windows/Linux network or install a resolver silently. The tool can open a verified current IP URL covered by its SAN when hostname resolution is unavailable. Duplicate names or an address occupied by another identity fail closed.

Start with 90-day leaf validity and renewal eligibility when 30 days remain, subject to proof that these bounds meet every qualified browser's current rules. The authenticated bootstrap may supply the desktop issuance-time observation when the device lacks a usable wall clock. Enrollment requires a plausible operator-verified current date and browser-valid certificate interval, not an Internet connection or currently synchronized NTP. Flag gross clock disagreement and stop for explicit clock correction; do not set an OS/device clock silently. Certificate wall-clock checks are independent of tighter RF/UTC admission and USB time qualification, which remain unchanged. A clock that cannot support certificate validation receives an actionable error, never a validity bypass.

Renewal, changed SAN addresses, key replacement, and epoch changes use prepare → desktop trust installation → explicit target activation → verified HTTPS probe → removal of superseded tool-owned trust. Device publication is atomic. Read authoritative target and local enrollment state after lost replies or restart; do not repeat an activation or remove the last valid entry blindly. A failed preparation keeps the admitted current leaf; a committed activation is reconciled rather than automatically rolled back. Other enrolled computers may need their own refresh before connecting; this workflow does not promise simultaneous availability across all clients. Because the browser trusts a leaf rather than a CA, desktops must refresh trust through the authenticated enrollment tool before accepting a new leaf. The tool performs generation, transfer, trust update, and cleanup; the operator may need to reconnect the trusted SSH/USB channel and approve OS prompts. Do not promise silent background renewal or permanent trust of a public key across certificate changes.

Let the helper open the verified current URL; it need not edit browser bookmarks. Old browser sessions and target bindings are not carried across changed origins or credential epochs. A certificate failure or address change cannot replay a mutation or rearm output. TLS renewal/reload must preserve backend scheduling and existing cleanup; use graceful frontend replacement where the qualified runtime permits it. Session-owned transient tone/output still follows its existing disconnect cleanup. A TLS change does not promise to keep a transient command alive or resume it automatically.

Offline operation needs no public domain, CA service, DNS validation, revocation server, telemetry, or Internet download at runtime. Valid dates, locally available enrollment software, a supported browser, and an authenticated bootstrap channel for initial enrollment/refresh remain necessary. Certificate expiration does not justify extending dates, suppressing verification, or falling back to HTTP. USB/local administrator recovery remains available.

## 6. HTTPS/WSS and application integration

For the current Linux Pi installation, terminate browser TLS in Apache using the existing same-origin application paths and proxy model. Allow TLS 1.3; do not add TLS 1.2 merely to support an unqualified browser. Only the credential owner and narrow TLS terminator may read the private leaf key. On Linux use a root-owned `0700` `/var/lib/wsprrypi/browser-tls` owner directory and `0600` private-key files, outside the web root and backend SQLite generation tree; Apache obtains the key through its admitted master/credential-loading lifecycle, not a world-readable copy. Reuse the existing bounded privileged maintenance lifecycle for typed prepare/activate/recover operations rather than creating a generic privileged daemon. The unprivileged browser/backend receives public metadata and typed results only. Pico needs an identity-bound, recoverable credential record in its existing provisioning/flash ownership model, with erase/transfer behavior, no source-tree/image key, and firmware-size/memory validation before activation. Keep the backend, browser runtime, and maintenance identities separate and preserve current network admission. Internal loopback/verified IPC traffic is a separate boundary; it must not become remotely reachable to bypass TLS.

Serve the page, scripts/styles/fonts, API, pairing display/submission, events, downloads/uploads, and WebSockets from the admitted HTTPS origin. Audit the complete route inventory, including Maintenance, support bundles, recovery, configuration, and auxiliary PHP endpoints. Remove direct browser fallback to ports 31415/31416 for the secure profile; a proxy failure is a visible error. Require WSS under HTTPS and reject cross-origin, null/malformed/duplicate authorities and untrusted forwarded metadata before mutation. Preserve exact Host/Origin/proxy/CSRF, body-size, rate, unknown-response, and request-id rules.

Use trusted termination context, authenticated by the existing proxy/IPC boundary, to establish scheme; never trust a client-supplied forwarding header or Origin as proof of TLS. Set Secure/HttpOnly/SameSite session cookies for secure browser use, bind them to the admitted origin/context, and retire them on trust/authority epoch transitions. WebSocket upgrades must receive the same authorization intended for the existing browser command lane; adding encryption must not bypass backend revalidation or release/cleanup semantics.

For direct Pico pages, add the necessary consumer HTTPS admission and public TLS material/provisioning resource without conflating engineering mTLS and ordinary browser authentication. Preserve existing password/Consumer-Radio protections inside the authenticated page, profile/journal/delivery rules, memory limits, time management, and response acknowledgments. Update the browser's HTTPS Origin/port and secure-context checks coherently. Inventory exact carrier/interface/port/method/resource admission rather than recognizing clients by User-Agent or broadening scheme allowlists. Transport provenance must establish whether the browser crossed TLS; a machine request must still satisfy its independent existing authority. Engineering HTTPS/mTLS, native Pi paired TLS, USB, and non-browser machine Consumer-Radio traffic retain their distinct authority and keys.

HTTP in a migrated secure profile serves only bounded, non-sensitive connection/enrollment guidance, or a redirect to an exact preconfigured HTTPS authority. A redirect is convenience, not bootstrap authentication; never construct it from arbitrary Host input. It serves no operational application or secret form. Handle virgin Pico/AP commissioning through the deliberately selected trusted USB/local workflow before secure browser configuration; keep independent BLE/USB provisioning intact. Any retained pre-migration HTTP browser mode is explicitly legacy and cannot be advertised as protected. The migration slice must enumerate its exact profile/interface exposure rather than leave an undocumented compatibility listener.

In the secure profile, bind plaintext HTTP/WebSocket frontend listeners to loopback or an equivalently restricted local endpoint and restrict access to the admitted TLS proxy path. Close the UI’s direct-port fallback. The backend must consume only verified proxy/IPC transport context, with the proxy stripping caller-supplied transport-identity and forwarded-scheme headers and supplying its own admitted identity. A claimed HTTPS Origin, X-Forwarded-Proto, network address, or cookie flag alone cannot authorize secure-browser traffic. Test direct LAN access to ports 31415/31416 and duplicate/spoofed proxy headers. Preserve separately registered machine/bootstrap/Consumer-Radio carriers with their existing cryptographic admission; an encrypted machine endpoint is not permission to serve the operational browser page over HTTP.

Port 80 may provide a bounded non-secret recovery/help page and a redirect to a configured verified HTTPS authority. Never derive that authority from untrusted discovery or arbitrary Host input. It cannot display/accept pairing codes, passwords, backup passphrases, private settings, control requests or browser WebSockets. Its page remains unauthenticated, so do not download or run enrollment software from it, treat its instructions as proof of device identity, or use it to weaken OS trust. Automatic HTTP fallback and an insecure operational compatibility switch are excluded.

Audit mixed content and third-party runtime assets. Bundle assets necessary for offline operation where already legally distributable; block active HTTP content and remove insecure endpoint fallback. Introduce response hardening, no-store for secrets, and a CSP through tested report-only observation followed by enforcement compatible with existing UI code; keep any violation observation local and redact URLs/payloads rather than introducing telemetry; do not rewrite unrelated frontend architecture. Where the qualified DNS/browser profile supports it, stage HSTS only after tested HTTPS recovery, starting at 300 seconds with no preload or includeSubDomains. Do not rely on HSTS for first contact, IP origins, transport authorization or downgrade prevention; a stale policy must not strand local recovery.

## 7. Pairing, ownership transfer, restore, and recovery

The existing Pi management-pairing protocol and purpose keys stay unchanged. The browser showing the target code and the browser submitting it to the managing device each require their own trusted HTTPS origin. Enrolling one service does not enroll its peers. Keep current code expiry, attempt limits, originating view/boot/device binding, cancellation, and uncertain-operation reconciliation. Never display or transport the code in URLs, discovery, logs, support bundles, analytics, shell arguments, or persisted browser storage.

Server TLS identity, machine pair authority, desktop trust entries, and browser sessions are separate records. Unpairing a machine does not automatically erase browser trust or revoke an authorized LAN user's access. This plan does not add user/client certificates or account roles; any requirement to revoke particular human browsers is a separate authorization decision, not a claimed effect of server TLS.

An explicit installation ownership transfer rotates the browser server key/epoch, retires local sessions and enrollment offers, and requires fresh enrollment. Keep machine ownership and schedule-retirement duties under their existing owners; HTTPS cannot clear unresolved RF/authority state. The desktop tool can remove its owned old trust entries when next run. An offline desktop cannot be forced to remove old trust, so do not promise instantaneous revocation of a copied old certificate/key; document the remaining impersonation window and local removal procedure.

Reinstall preserves established identity and credentials or refuses for recovery; it must not silently regenerate a device identity or make old enrollment records apply to a new device. Integrate credential recovery with the existing recover-versus-move owners. Every confirmed credential-bearing restore must produce a fresh browser TLS key and epoch before browser control resumes; a same-installation recovery may preserve device identity but still requires desktop re-enrollment. A move preserves destination identity and never activates the source browser key. Exclude browser TLS private keys and desktop trust entries from newly created application backups; they are not needed to restore settings. Explicit recovery regenerates them through the credential owner. Old TLS material encountered in an earlier archive is not current serving authority and cannot be installed as an opaque file. Use a fresh unpredictable epoch component rather than claiming that an offline backup can prove a globally latest counter. Preserve protected recovery evidence, and keep interrupted restores held. Never restore transient browser sessions as current permission. Protect keys and credential metadata with owner paths/ACLs, exclude them from diagnostics/plaintext exports, and add native Mac/Windows ownership adapters for enrollment state only.

Recovery is local administrator/verified SSH or the selected USB management channel when HTTPS is unavailable. It can inspect identity/time/certificate state, prepare a new leaf, and remove tool-owned trust after explicit consent. It does not start transmission, reset pairing, clear restore holds, or edit arbitrary trust stores. Installation/renewal failure retains coherent prior state or an explicit held/error state; never silently reopen HTTP controls.

## 8. Mobile boundary

The selected scope is desktop enrollment and offline LAN operation. iPhone/iPad and Android remain evaluated, not advertised as supported by the desktop leaf-trust design. Mobile browsers may require private-CA trust: iOS requires explicit profile installation and SSL trust unless managed deployment supplies it; Android requires an OS certificate-install workflow and browser-specific validation. A desktop's trust record does not enroll a phone.

Supporting mobile through a private CA, MDM/Configurator, a native app, or public-domain certificates requires a separate choice before implementation. Broad CA trust is not a hidden fallback. Preserve responsive UI review on desktop browser viewport emulation, but do not present that as mobile TLS qualification. Record direct mobile HTTPS as unqualified until a selected mobile trust workflow passes on real devices.

## 9. Ordered implementation slices and approval gates

1. **Trust feasibility and contract freeze:** Inventory exact routes/listeners/profiles/consumers, trust stores, existing ownership and key paths; run disposable browser experiments for the leaf-trust matrix, malformed/wrong-peer/child-certificate refusal, renewal and removal. Freeze exact OS/browser baselines, credential/document schemas, SAN policy, native store operations, capacities, issuance-time rules, and package verification. Gate: leaf trust meets the agreed matrix without broader CA authority or verification bypass. Failure requires a focused decision before dependent implementation.
2. **Credential and enrollment owners:** Implement device-local key generation/public enrollment export and the narrow desktop bootstrap/store adapters. Preserve SQL/identity/recovery owners, USB roles and machine protocols. Test interruption, explicit consent, wrong physical/logical device, renewal, private paths and uninstall ownership. Gate: no private-key export, arbitrary trust import, unowned store modification, or automatic device substitution.
3. **Secure service integration:** Add Apache HTTPS/WSS and required Pico consumer HTTPS handling; update all browser-facing routes, proxy/session context, URL construction, descriptors, validators, generated clients and tests together. Gate: no plaintext page/code/control bypass in migrated profiles; actual retained management works. Normal TLS credential operations must not disrupt autonomous execution or silently resume held work.
4. **Migration, pairing and recovery UX:** Provide explicit preflight, enrollment/readback/secure-origin test, then HTTPS cutover with local recovery available. Verify each actual browser before retiring its previous access path. Keep drafts, unknown outcomes and current safety controls intact. Do not deploy partial profiles or remove the sole recovery path. Gate: pairing code visible/submittable only on the authenticated page; upgrade, renew, move and transfer behaviors are coherent.
5. **Documentation, integrated validation and adversarial closure:** Complete exact-source tests, desktop/native trust evidence, rendered operator docs, and the full review loop. Gate: every supported claim has evidence, every required companion change is in the intended source pair, and no required test/documentation work is outstanding.

A later full implementation instruction may authorize all slices and named repositories; a slice-limited instruction authorizes only that slice. Plan approval starts none. Broader CA trust, mobile support and #7's host port are not implicitly authorized. No deployment, trust-store mutation on the user's computers, services, firmware installation or RF exercise is authorized by this document.

## 11. Assessment loop and remaining decisions

Assess the entire plan/implementation against the threat model, route inventory, source pair, package/trust lifecycle, user workflow and acceptance matrix. Fix actionable in-scope findings, rerun affected checks, then perform another full assessment including retained paths and recovery. Repeat until a full pass finds no further actionable finding. Reopen affected evidence after subsequent edits. Missing qualification is a named gate, never a clean assessment or broad readiness claim.

The user selected desktop enrollment with offline LAN operation. The architecture excludes broad CA enrollment and public-domain dependencies. Remaining implementation prerequisites are the leaf-trust feasibility result, exact native browser baseline/proof, explicit cross-repository and disposable-host execution scope, and a separately authorized package-signing/distribution arrangement where native platform policy requires it. If leaf trust fails the agreed matrix, obtain a design decision; do not shrink the matrix or add CA trust silently. Mobile CA/app/managed enrollment and human-client revocation remain separate product choices. These are explicit gates, not claimed implemented capabilities.

Completion requires implemented and documented protected browser paths, passed exact-source integration and qualified desktop trust/profile tests, demonstrated recovery, and an accurate report of remaining physical/deployment limits. This plan alone completes none of those implementation gates.
