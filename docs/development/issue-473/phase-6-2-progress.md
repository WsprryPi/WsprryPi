### P62-02 — durable automatic-rotation intent (approved 2026-11-17)

The approved rotation sequence has a crash gap before the controller has durably derived its next TLS key: the target may have accepted `rotate/prepare`, while the controller loses the reply and restarts. The exact retained reply supplies the target's public share, but the controller cannot reconstruct its own fresh ECDH private key from the approved PairRecord fields. Discarding that prepared rotation, silently starting another one, deriving a nonfresh key, or requiring another human pairing code would violate the approved exact-operation/automatic-lifecycle contract. This proposal closes that gap without a wire or operator-workflow change.

Approve a bounded private rotation-intent continuation in the device-owned version-1 pairing operation book. Its exact fields are `{kind:"rotation-intent",self_id:ID,peer_id:ID,profile_id:ID,pair_id:ID,authorization_generation:Generation,operation_id:ID,expected_epoch:Generation,stage:"awaiting_prepare"|"awaiting_commit",prepare:RotatePrepare,prepared:RotatePrepared|null,private_key:B32|null}`. `prepare` and `prepared` use the existing closed Pair/1 messages; duplicated pair/operation/epoch fields must match, and next epoch must be exactly current plus one. `profile_id` identifies the existing server-owned logical target context; no browser chooses a private path. Public/derived key checks remain with the existing OpenSSL crypto owner.

Before sending the first prepare request, atomically save the exact prepared request and a fresh OpenSSL-generated P-256 private key in the private operation book (`awaiting_prepare`, `prepared:null`, nonnull `private_key`). Export/import uses OpenSSL's standard key APIs and fixed 32-byte canonical encoding, with provider validation; no hand-written curve arithmetic or deterministic substitute is permitted. The record is 0600 inside a 0700 owned namespace, with bounded no-follow reads, file/directory sync, the existing WAL version 1 and six-image bound, and the existing 256-terminal/32-unresolved receipt bounds. This is private recovery material, never an operator receipt, browser document, log, support-bundle input or manual key file.

After validating the retained prepare reply and deriving the next TLS key, atomically publish that key in the existing PairRecord pending slot and replace the private continuation with `awaiting_commit`, the exact prepared reply, and `private_key:null`. The controller can then finish/read back the exact existing rotation automatically after a crash. Completion or access revocation erases the continuation's private key through the same complete decision; unresolved operations cannot be evicted to make room. Previously authorized epochs retain only their already approved scoped recovery privileges, and generation revocation wins over every epoch. Initial-pair commit keys and temporary human codes are not added to durable storage by this proposal.

PairRecord fields, Control/1, Pair/1 messages, TLS profiles, WTP, Pico authentication, scheduling and operator actions remain unchanged. The user explicitly approved this private-key retention policy on 2026-11-17; implementation and validation remain unfinished. AGENTS.md's rule, "If an ambiguity would materially change behavior, compatibility, persistence, hardware operation, or user workflow, stop and ask for direction," applies to this previously unspecified durable retention of an ephemeral rotation key. Independent validation and already approved ownership work continue.
