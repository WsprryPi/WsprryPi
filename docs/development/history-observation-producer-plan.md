## Outcome and boundaries

An explicitly provisioned local History reader can discover a closed observation contract, read bounded execution observations, and obtain an approved current-state baseline without receiving control, private settings, pairing credentials, database access, or hardware authority. Completion evidence preserves source outcomes and the accepted execution context actually available. A missing observer, slow reader, malformed request, restart, or overrun cannot alter transmitter admission, scheduling, execution, cancellation, or existing Pico USB collection.

| Ownership | Work in this plan |
| --- | --- |
| WsprryPi | Dedicated producer endpoint, observer authorization, approved runtime evidence capture, bounded volatile retention, source schema and fixtures, lifecycle integration, opt-in producer provisioning, tests, and engineering documentation |
| Wsprry-History | Journal reader/helper, helper-to-forwarder socket, spool and persistent checkpoints, journal allowlists and parsing, source reconciliation, credentials and outbound HTTPS, central ingestion, database, dashboards, deployment, and its operator documentation |
| WsprryPico | Existing observations only; inventory actual available identity, terminal evidence, and bindings. No new firmware capability or carrier access is assumed |

The first implementation targets a filesystem Unix-domain endpoint on Linux stations. macOS and Windows controller behavior remains supported and unchanged; the optional Linux observation facility is unavailable there, with no TCP, named-pipe, root, or broader-role fallback. Supporting History collection on additional operating systems requires separate scope. Native Pi executors are covered; managed Pi/Pico observations are exportable only where existing production owners already provide authoritative identity and execution-bound evidence. Do not advertise a device as supported merely because it appears in the Fleet selector.

Do not implement the History collector in WsprryPi. Do not add remote inbound observation listeners, browser controls, a public HTTP API, persistent transmission tables, a durable application event archive, journal retention changes, log-level changes, new Pico ports, automatic logging enrollment, additional consumers, or new calibration instrumentation. Existing browser presentation and current control APIs remain unchanged. Missing evidence stays unavailable; additional producer fields or companion changes need explicit review rather than invented values or implicit expansion.

## Existing evidence and gaps

- `src/application_control/local_transport.hpp` defines administrator and web-service principals and existing control/event/browser channels. `local_transport.cpp` verifies those peers; neither role is an acceptable identity for the History helper. A group-readable existing event socket is not the required authorization boundary.
- `src/application_control/event_feed.hpp` supplies a bounded, volatile browser-oriented feed with resynchronization. It is not a durable History archive or a History schema. Reuse safe low-level primitives only when they preserve independent dispatch, authorization, bounds, and worker capacity.
- `src/scheduling_runtime.cpp` distinguishes completion, skip, cancellation, and failure paths. `src/scheduling_websocket_status.cpp` maps finished and skipped to the same presentation state. Capture lifecycle evidence before that mapping, with the actual execution generation and accepted context; do not infer success from a UI label or idle snapshot.
- `src/scheduling.hpp` exposes useful WSPR status and correction provenance. Inventory each field's actual owner and lifetime before reuse: a mutable status snapshot is not automatically historical accepted execution context. The existing imported Pico USB path retains different source and trust semantics; observation export must not acquire another USB handle.

## Contract and evidence design

### Execution capture and identities

At admission, build an immutable, bounded observation context from the accepted execution request/plan under its owning synchronization. Assign a producer-boot-scoped run identity and per-frame identity where no existing suitable identity exists; these are observation identifiers, not changes to shared control identifiers or persistence. Map callbacks through the actual owner/generation, never through whichever request is currently displayed. Capture minimal accepted context before mutable settings, plan advancement, reload, or cleanup can replace it. Reject stale callbacks for a newer execution and record safe gap/conflict evidence where attribution is uncertain.

For native Pi execution, publish successful completion only after the authoritative successful terminal path, including required cleanup result, establishes it. Inspect the actual callback/controller contract before choosing the hook: an outer COMPLETE callback or log message alone must not conceal cleanup failure. Preserve per-frame outcomes and distinguish one completed frame from a completed multi-frame plan. Cancellation, skip, failure, interrupted cleanup, admission without execution, and ambiguous attribution never become successful completion. Test Tone and indefinite sessions must not be reclassified as completed finite transmissions because they stopped normally; explicitly exclude unsupported lifecycle kinds from completion eligibility.

For managed executors, preserve physical executor identity, device boot, controller identity, assignment/profile binding, source/carrier, trust classification, and existing execution/job/frame bindings separately. Do not substitute controller success for device completion, alias controller boot as device boot, or deduplicate different devices by job number alone. Only owner-validated existing terminal evidence may establish a remote completion. Unavailable network-only or USB evidence is an explicit source limitation; new Pico protocols are outside this plan. Reassignment must end the old observation scope, invalidate incompatible positions, and never relabel old records as belonging to a new device.

Use separate context and terminal record types so incomplete attempts can remain bounded assembly evidence without becoming History transmission rows. Include only fields needed to bind a terminal outcome to its accepted context. Context includes available mode, accepted frequency and its defined meaning, WSPR placement/frame metadata, normalized accepted callsign/locator, advertised dBm, backend/profile, and available execution-bound correction provenance. Exclude arbitrary message bodies, raw settings, credentials, private paths, and unrelated diagnostics. Do not equate requested frequency with realized RF frequency or advertised dBm with measured output. An absent correction chain affects advisory eligibility, not otherwise established completion.

### Dedicated producer protocol

Use the independent contract identifier `wsprrypi.history-observation`, major 1. It does not change shared settings/control major, transport authentication, or storage versions. Check in closed machine-readable request, response, descriptor, context, terminal, snapshot, and loss schemas and canonical positive/negative fixtures. No historical views, version-range negotiation, hidden fallback, generic dispatch, arbitrary filters, SQL, paths, journal queries, or mutations are allowed.

| Operation | Semantics |
| --- | --- |
| `describe` | Exact contract identifier/version, producer boot, supported source kinds and eligibility, policy revision, units, limits, and capabilities; no saved configuration dump |
| `snapshot` | Bounded current approved contexts and source availability with an associated producer event watermark; no claim of historical completion from current idle state |
| `read` | Bounded records strictly after a valid opaque position, with next position, observed head, more-available flag, and explicit coverage/resynchronization status |

The producer's runtime stream is distinct from the History helper's journal stream. Requests address only the producer stream; the helper owns journal positions and source merging. The descriptor/snapshot supplies both a head baseline and an opaque position immediately before the oldest retained record, so a new consumer can traverse the retained window without manufacturing a cursor. Selecting the head deliberately skips prior retained records and requires a History-side coverage decision; a snapshot watermark does not authorize silently dropping unread events. Producer reads do not acknowledge local spool durability or central delivery. Retrying a valid runtime position returns the same retained records or explicit expiration/overrun; disconnect does not advance server-side consumer state.

Use four-byte unsigned big-endian length framing followed by one UTF-8 JSON document. Apply the History trial limits: 8 KiB request wire size, 16 KiB individual observation size, 128 KiB complete response/snapshot wire size, 32 observation/rejection items per page, 4 KiB continuation, 16 nesting levels, and five-second total request deadline. Include the framing header in request/response limits; measure serialized UTF-8 bytes including escaping and envelopes. Return available data promptly; no long polling, compression, arbitrary blobs, or fragmentation. Reject length overflow, invalid UTF-8, duplicate keys, excessive depth, trailing data, extra/missing fields, wrong types, invalid ranges/units, unknown operations/versions, and inconsistent identities before field consumption or source reads.

Represent nanosecond times and potentially large counters as canonical decimal strings. Retain UTC and monotonic observations with explicit clock domain, source precision, and availability; clock steps must not reorder producer sequence. Fields have explicit known/unavailable forms with fixed reason codes, not guessed zeros, empty strings, current saved settings, or implicit JSON coercion. Define exact byte/string/numeric/array bounds for every schema field before code; the serialized context plus terminal relationship must fit the observation/page ceilings. An oversized eligible item yields a bounded loss/rejection record, never truncated valid evidence or a checkpoint silently moved beyond it.

Positions are bounded opaque encodings of a closed tuple: contract/policy revision, producer boot, stream epoch, and sequence. They contain no caller-selected source selector or permissions. Validate them against the authorized stream and current retained range; positions are not credentials and need no secret embedded in them. Unknown boot/policy, impossible future position, malformed encoding, or expired range yields a fixed refusal/resynchronization status. Do not silently clamp to a nearby position or current head. A repeatable loss item may identify a rejected producer sequence without echoing the rejected payload.

### Consistency, resource limits, and failure behavior

Use a separate volatile observation store with trial bounds of 256 records and 4 MiB total retained record bytes, whichever binds first. Bound auxiliary contexts, identities, serialization buffers, workers, sockets, and rejection bookkeeping separately; count them in the measured total process overhead. This is bounded live replay, not retention of all transmissions. Descriptors expose the actual retention bounds and positions, not a guaranteed time window. Slice 1 must specify the maximum tested event rate, reader cadence assumption, and callback latency/resource acceptance budgets; validate them against production frame bursts, and expose loss when exceeded rather than promising gap-free collection. Reader scheduling remains a History responsibility. Immutable accepted context must accompany each eligible terminal record, directly or through context retained with the same replay lifetime; never evict a context while claiming its dependent terminal record remains fully interpretable. If a complete minimum record cannot fit, return explicit evidence loss rather than expanding bounds silently.

Publish through a fixed-capacity nonblocking handoff. Scheduling/backend callbacks never wait for socket I/O, reader progress, JSON serialization, journal access, or a consumer-held mutex. Contention/capacity failure increments bounded atomic loss metadata and invalidates seamless coverage even when no loss record fits. The next successful read or snapshot exposes the loss epoch/range or explicitly unknown range. Sequence assignment, publication, loss reporting, and snapshot watermark use one documented ordering model; a watermark must never claim an accepted-but-unpublished record was available.

Prefer consistent snapshot plus watermark under the existing execution owner, with expensive encoding outside its locks. Establish a lock-order and generation-fencing proof before implementation. If a coherent snapshot cannot be obtained within bounded work, return snapshot unavailable/retry with coverage uncertainty; do not silently use two independent reads and claim consistency. Snapshots can be truncated only through an explicitly defined incomplete/unavailable response, never an apparently complete partial list. No new polling thread may access live mutable configuration unsafely.

One authorized reader is supported, with one outstanding request. Use separate observation worker capacity from control, browser, and USB workers, finite accept/backlog limits, per-connection byte/time bounds, bounded parse/scan work, and deterministic shutdown cancellation. Additional or stalled connections are refused or closed within the deadline. Eviction, producer restart, disabled endpoint, policy revision, assignment change, and unavailable sources produce explicit health/coverage results. Persisted checkpoints and their atomic commit with spool records remain History responsibilities. The producer writes no new archive and does not promise recovery after restart.

## Local authorization and optional provisioning

Use `/run/wsprrypi-observation/producer.sock`, separate from existing application sockets. On installed Linux the existing backend owner creates the protected directory (`0750`) and listener (`0660`) with dedicated client group `wsprry-history-observe`. The authorized non-login helper account is `wsprry-history-reader`; its numeric UID is resolved once for the producer lifetime. The History forwarder receives neither this group nor the producer path. The helper and forwarder must not share a UID or reuse root, backend, web-service, maintenance, or operator identities. Reject account collisions and unsafe incidental memberships.

The backend verifies the exact helper UID using kernel peer credentials on every accepted connection; filesystem group membership alone is insufficient. The helper verifies the expected backend peer and protected endpoint ancestry. Root remains trusted. Do not add an observer principal to generic administrator dispatch. Use a dedicated closed dispatcher and no access to the diagnostic settings export. Existing control/browser/private-state permissions remain unchanged.

Producer enablement is opt-in, Linux-local process configuration, disabled by default. Introduce one documented producer enable option integrated with the existing runtime-option parser; no browser setting or persisted shared device setting is needed. Exact option spelling and installed service override location are frozen in the first contract slice. The History deployment owns reader/forwarder service installation, account/group provisioning, and its journal permissions; WsprryPi documents and validates the producer prerequisites rather than installing History services. Do not restart or modify running services during development validation. When explicitly enabled, missing/conflicting identity or unsafe paths leave observation unavailable with a bounded diagnostic while ordinary transmitter behavior continues; never fall back to root or the web account. Disabled mode creates no new listener and requires no History accounts.

Validate every parent directory, symlink/type/owner/mode, expected endpoint ownership, and numeric principal before binding. Clients cannot write the socket directory. Remove a stale socket only after verifying the expected owner/type and proving there is no active listener; refuse ambiguous or suspicious paths without repairing them. Define backend restart/shutdown ordering and remove only the endpoint owned by that instance. Avoid socket activation initially so server-peer ownership and listener lifecycle stay explicit. Producer-side packaging fixtures verify permissions and opt-in behavior without executing installation or service targets.

## Implementation slices and deliverables

Each slice requires explicit authorization before starting; do not silently proceed into the next slice. A slice is not permission to deploy, operate hardware, or modify another repository.

1. **Contract and feasibility.** Reinspect actual execution owners, terminal/cleanup ordering, identity/assignment lifetimes, managed-device observations, and current platform profiles. Produce the source-to-field/eligibility matrix, exact schemas and field bounds, runtime option name, resource accounting, lock/order design, safe deployment prerequisites, and paired-source/dependency manifest. Cross-check the History plan. Identify unavailable evidence explicitly. Stop for a separate scope decision if a necessary producer capability, reusable-component modification, companion change, UI, or unsupported-platform expansion is required; do not design around mismatches by relaxing validation.
2. **Native evidence store.** Add minimal parent-owned capture hooks and the bounded store, immutable contexts, terminal qualification, sequence/loss semantics, and consistent snapshots. Cover local modes/frame plans and noneligible lifecycle kinds. Keep browser fields, execution ownership, and reusable transmitter interfaces unchanged unless a separately approved component fix proves necessary.
3. **Observation transport and lifecycle.** Add strict schema parsing/serialization, capability discovery, validated runtime positions, UID isolation, separate bounded workers, runtime opt-in configuration, safe paths, shutdown handling, and Linux packaging/provisioning fixtures. Keep disabled/non-Linux builds and normal service ownership unchanged.
4. **Production integration and handoff.** Exercise native execution and existing managed Pi/Pico observations through actual owners, both required carrier suites, observer denial/fault isolation, and restart/recovery scenarios. Publish canonical fixtures and the source map for the future History helper; do not implement that helper or collector. Complete engineering/operator documentation review and report source revisions, commands, remaining limitations, and separate installation/hardware gates.

If a managed source lacks the required supported evidence, its descriptor and source map must state it is unavailable for completion export. That is a transparent limitation, not completion of a requirement for that source. A slice-1 acceptance decision must approve the source eligibility matrix before code begins; required-but-unavailable sources block delivery unless separately scoped or explicitly excluded.

## Decisions and adversarial review record

Selected boundaries are optional Linux-local producer only, independently versioned closed observation schema, exact helper UID authorization, separate endpoint/workers, bounded volatile replay, immutable accepted evidence, explicit loss, and no new Pico capability or collector implementation. Schema layouts, field bounds, runtime-option spelling, lock details, and actual per-source eligibility are mandatory slice-1 deliverables, frozen and reviewed before executable implementation. They are engineering feasibility gates, not permission to invent behavior while coding. No additional product decision is needed to begin that authorized contract-design slice; unavailable required source evidence or an upstream-plan conflict must return for a scope decision.

First adversarial pass addressed overclaiming completion from presentation state, cleanup ordering, mutable accepted context, remote identity confusion, nonfinite/Test Tone eligibility, dependent-context eviction, overflow without room for loss records, default account provisioning, and scope leakage into the collector. The independent second full pass addressed caller positions as authority, inconsistent snapshot watermarks, blocking scheduling hooks, installed versus portable identity assumptions, unavailable-source completion claims, missing pair-suite gates, and unauthorized documentation/repository work. A further replay review added an explicit oldest-retained starting position, distinguished head baselines from durable consumption, and required declared event-rate, reader-cadence, and callback-budget acceptance assumptions. Reassessment against the scope, ownership, source contract, security, concurrency, replay, validation, documentation, and delivery criteria found no further actionable planning findings. This record qualifies the plan only; implementation feasibility and runtime acceptance remain unvalidated.
