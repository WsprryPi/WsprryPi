3. Define the saved-state and activation model

Before implementation, write a concise design and acceptance record.

- Unsaved browser edits.
- Valid fields durably saved on the Pico.
- Incomplete saved drafts.
- Complete applied configuration.
- Active boot configuration.
- Schedule enablement and STOP/suspension.
- Readiness for the selected operation.
- Ownership, loaded/armed/running jobs and actual output state.

Define independent fields and coupled validation units. Document omission,

Where complete Config v1 or a ConsumerProfile cannot represent incomplete
progress safely, introduce a small bounded durable draft representation.
Do not insert fake callsigns, locators, messages or reported-power choices.

Handle an already-enabled complete configuration explicitly. Saving a draft
must not silently replace its live station or resume STOP. If existing
scheduled operation continues using previous applied values, show that fact
beside the draft's incomplete/readiness state.

Choose the smallest implementation that satisfies these requirements through
the existing configuration and provisioning authority. Avoid a second scheduler
or a parallel configuration authority.

4. Save independent valid progress

At minimum, support and test:

- Callsign-only saving with no locator or message setup.
- Locator-only and reported-power-only saving.
- Valid settings when unrelated controls are blank or invalid.
- Mixed valid/invalid edits: save valid independent values, retain invalid
  browser edits unsaved, and clearly identify each outcome.
- Existing complete settings: preserve unchanged authoritative components
  without requiring their re-entry.
- Device persistence across page reload, session turnover and reconstructed
  runtime/journal reload after reboot.
- Explicit completion and application of a previously incomplete draft.

Zero dBm is valid. Do not convert a blank numeric input to zero.

Preserve unchanged values. Treat an explicit clear differently from omission.
Do not manufacture unrelated Wi-Fi credential replacements when saving identity.
Existing authentication and step-up requirements still apply.

Validate coupled settings as meaningful units. Do not apply half a conflicting
pin plan, incomplete credential pair or invalid schedule array. Explain which
unit remains incomplete or unsaved while accepting unrelated valid progress.

The current send-only QRSS/FSKCW/DFCW form must not block settings saves.
Keep its explicit Load and arm action distinct from saving settings.
Do not add a general message library or persistent raw-job store incidentally.

Preserve the existing atomic semantics of legacy PUT, config-update/1 and
versioned station/config operations. An invalid member of an old atomic request
must still reject the whole request without partial mutation.

If field-level partial success needs a new operation, advertise and version
it explicitly. Define strict per-field outcomes, target/revision binding,
bounds and authoritative readback. Prefer one bounded verified commit of the
accepted independent progress over multiple unsynchronized browser writes.

Never silently retry a subset, discard validation failures or replay a write.
