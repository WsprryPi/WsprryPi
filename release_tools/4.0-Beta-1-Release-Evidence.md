## Starting code review

The review compared actual devel capabilities and commit history, not only the
October 17 checklist. Focused contracts included configuration/persistence,
protected browser routing, the native consumer/USB/TLS adapters, WTP planning and
runtime admission, Pico progress authority, firmware maintenance, Fleet,
container/version metadata, RP1 acceptance and the operator Docs.

Component READMEs checked included WTP-Client, WSPR-Transmitter, WSPR-Reference,
Chipset-Offsets, Mailbox and PPM-Manager. There are zero tracked gitlinks. The
only first-party component modified for this preparation is `WsprryPi-UI`;
`src/wtp_integration` and the runtime bridge are parent application integration,
not changes to the portable WTP-Client or transmitter/reference libraries.

Findings shaping the scope:

1. The checklist's old current Pico reference and unstarted Beta status omitted
   later USB control/UTC, drive, firmware installer/erase/recovery, visible Fleet
   and rate-limit work. Historical acceptance remains historical; source inclusion
   is reconciled here.
2. Pi already exposed independent station progress over USB, but network carriers
   lacked that route and the USB path forwarded unvalidated remote replies. One
   selected-member coordinator now validates discovery, bounded data, exact
   revisions/identity, independent outcomes and actual saved effects on all four
   supported management carriers. Complete atomic APIs remain intact.
3. Existing tag-derived build metadata would call an untagged candidate 3.2.0
   devel. An explicit validated candidate build override now emits 4.0.0-beta.1
   while preserving attribution. Ordinary builds retain their existing behavior.
4. Operator Docs explicitly said Pi could not retain incomplete fields. The
   separately committed update removes that contradiction and documents the
   new save/read/discard/apply workflow.
5. The historical Build Orchestration guide creates/amends/retags a release.
   It was inspected as historical context and was not executed; this preparation
   uses the bounded candidate override and stops before publication.

This was a focused release/source review, not a line-by-line audit of all 1,852
changed paths or general hardware/RF qualification.

confirmed compatibility changes and uncertain risks. Explicit operator actions

### WTP/1, Fleet and network control

WTP/1 is the device-neutral finite-job protocol. Complete `rf-events/1` jobs
are loaded before ARM; the member's local clock/engine owns event timing.
WTP/1 does not define stored schedules, station/hardware configuration,
provisioning, browser APIs, firmware maintenance or RF filtering. Separately
versioned management resources cover those functions.

The controller can run zero through eight remote assignments alongside its
local schedule. Each assignment has an independent mode, RF base frequency,
repeat period and UTC phase. Fleet WSPR assignments are single-frame jobs;
selected-Pico Type 2/3 station planning is not a promise that the assignment
editor supports every extended WSPR plan. Native Pi members use their selected
GPIO, RP1 GPCLK or Si5351 backend. Current CAPS and host frequency/route policy
must accept each job.

Remote dispatch requires `--allow-unqualified-frequency` or
`[Experimental] Allow Unqualified Frequency = true` on the controller.
Outside-amateur-band requests require the separate existing opt-in. RP1 retains
its exact-operation host confirmation. Saved profiles, discovery and successful
capability inspection grant none of those overrides.

Profiles retain explicit device identity and connection settings. DNS-SD
observation is link-local and not authentication; routed/VLAN deployments need
manual endpoints. USB, Plain LAN and authenticated Pico TLS share WTP/1 job
semantics, without automatic transport downgrade or endpoint retargeting.
The Pi listener provides Plain LAN, not TLS; Plain LAN does not authenticate
individual users or encrypt traffic. Browser network-location guards are
separate from transport authentication.

Failed/uncertain assignments pause independently, consumed slots are not
replayed, and successful reconciliation leaves the assignment paused. A lost
connection, expired result or changed boot is not output-off evidence. Local
Pi takeover revokes future remote assignments through durable takeover history;
the controller has no veto. Unconfirmed output-off blocks reuse.

### Pico management and firmware compatibility

Configuration saves negotiate supported preservation/update capabilities rather
than erasing fields an older controller does not understand. Stale, ambiguous
or unsupported replies preserve drafts and require explicit readback/review;
a mutation is not automatically replayed. The Pi station editor consumes
`transmitter-progress/1`; newer amplifier-aware progress views can be refused
and require the corresponding Pico controls. Consumer profile-owned application
remains in Pico transactional setup. Complete atomic APIs and old-firmware
complete-save behavior retain their own supported scope. Test reference commits
are not firmware-image pins or acceptance of every later firmware combination.

Pico drive supports nominal 2/4/8/12 mA only with the advertised descriptor.
Saved value, active-at-boot selection and pad readback are distinct; 4 mA is the
Pico default. Drive is separate from reported WSPR dBm and measured RF power.
Host USB UTC delivery requires qualified clock observations. New WTP settings
use 100,000,000 ns (100 ms) maximum admitted uncertainty; explicit existing
limits, including 1 ms, are not silently increased. UTC synchronization does
not calibrate RF frequency.

The USB firmware selector defaults to Pico `main` independently of the Pi
branch. Missing images are refused without substitution. Compatible installer
updates are independent of Pi releases; active recovery keeps its original
verified installer snapshot. BOOTSEL handoff, exact-device identity, retained
maintenance holds, backup and continuation are governed by the installer
contract. Full erase verifies all 4 MiB blank, removes persistent flash data,
creates no new backup and leaves BOOTSEL; ROM/OTP/immutable identity are not
flash erase targets. Unresolved maintenance is not bypassed by deleting markers
or downgrading. Draft and credential formats can survive firmware downgrade.

USB maintenance requires Python 3.10+ and USB-enabled picotool >=2.3 within 2.x;
Pi deployment does not install picotool or the Pico SDK. Management carriers,
resource revisions and permission boundaries remain in the engineering guides.

### Bands, calibration and RF qualification

The canonical catalog contains 19 bands, 2200 m through 70 cm. The retired
22 m entry is removed; `lf`/`mf` remain aliases for 2200 m/630 m. 8 m and 5 m
require deliberate preferences, and 60 m has legacy/WRC-15 presets. Catalog
membership, numerical backend capability, measured qualification and operating
permission are separate facts.

Recorded Si5351 WSPR acceptance includes 2200 m, 630 m, 160 m, 6 m, 4 m and
2 m on the actual documented setups. Useful mode-specific partial results are:

| Legacy 500 MHz GPIO, 2200 m | TONE, QRSS, FSKCW and DFCW accepted; WSPR unqualified |
| BCM2711 GPIO, 6 m | TONE, QRSS, FSKCW and DFCW accepted; WSPR unqualified |
| Si5351, 2200 m | TONE, WSPR, QRSS, FSKCW and DFCW accepted |

These results do not qualify other hardware, clock parents, outputs, loads,
calibrated power, absolute frequency or spectral performance. Experimental
permission does not admit an Unavailable plan. The failed Si5351 70 cm
third-harmonic proposal is not shipped support.

GPIO correction separates the qualified system-clock estimate, measured
residual, manual fallback and intrinsic processor/parent-clock offsets.
Positive GPIO PPM describes a fast source clock and corrects requested RF
downward. Effective correction freezes for each transmission. A previous total
manual correction must account for the intrinsic term to avoid double counting.
Legacy `GPIO.Use NTP` migration preserves supported values and canonical-key
precedence; `--use-ntp` is removed in favor of
`--use-system-clock-frequency-estimate`. Si5351 uses its own reference/manual
PPM and does not consume the GPIO estimate.

The legacy GPIO TONE repair removes the nominal -2.197265625 Hz WSPR-table
symbol-zero displacement. It is separate from oscillator correction and
synthesis quantization. Si5351 readiness checks and error containment retain
cleanup errors separately; previous SYS_INIT failures on one setup remain
unexplained despite accepted bounded inhibited checks. A successful disable
write/readback is not an RF measurement.

### Platform, installation and maintenance details

The binary matrix is ARMv6 hard-float/AArch64 × Bookworm/Trixie userspace.
Bullseye and a separate ARMv7 export are outside it. Local precompiled mode
validates ELF architecture/ABI, loader, library/symbol resolution and version
before replacement; it skips application compilation/swap preparation, not
runtime packages, supporting files or optional RP1 module prerequisites.
RP1 needs compatible kernel headers and DKMS/build tools. Source preflight
separates RAM, zram and independently backed swap; temporary build swap is
installer-owned and cleaned up without replacing existing swap.

The installer preserves current persistent WTP keys, custom uncertainty,
WSPR profile/preferences and supported selector keys, and performs the supported
legacy GPIO migration before stock defaults can hide absent canonical values.
Failed/empty merge stops publication. Supported service-mask recovery,
noninteractive logging, ownership-aware provider removal and idle route/reboot
restoration have the exact source/test/target dispositions recorded above.
Installing or selecting an RP1 route never grants RF permission.

Update detection requires eligible release or positive ancestry evidence.
Packaged UI identity, installed UI classification and running-service identity
are independent. Modified UI backup, cache refresh convergence, real version
metadata and the WSPR encoder's stale-callsign repair retain their existing
source evidence. Missing/malformed Pi revision data fails closed rather than
fabricating BCM2835 identity. Components are ordinary tracked parent content;
there is no separate component-pull update procedure.

The directly connected physical-LAN browser guard does not require an Internet
route; it does not add individual authentication or encryption. Discovery needs
Avahi support. The managed inbound Plain LAN server defaults on after confirmed
startup quiescence, port 31417, with physical-interface selection. Support
collection remains local unless consented intake is invoked; the reviewed bytes
are encrypted under signed destination policy, and opening the upload service
is not confirmed delivery.

[container builds](../docs/container-builds.md),
[RP1 acceptance](../docs/rp1-provider-acceptance.md), and the issue/commit
reconciliation above. Backend profiles and the explicit simulator remain
engineering/CI features; simulation never substitutes automatically for failed
hardware and does not qualify physical operation.
