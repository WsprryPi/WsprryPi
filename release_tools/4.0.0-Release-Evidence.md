# Wsprry Pi 4.0 Beta 1

**Testing prerelease.** Changes since
[v3.2.0](https://github.com/WsprryPi/WsprryPi/releases/tag/v3.2.0).

## One station, a fleet of transmitters

**Wsprry Pi 4.0 lets one Raspberry Pi control a mixed fleet of other Pis and
WsprryPicos while continuing its own local transmissions.** Manage up to
**eight remote outputs**, each with its own mode, frequency, message and
schedule, from **Setup → Fleet**.

This is made possible by the new **WsprryPi Transmitter Protocol, WTP/1**.
It gives Pis and Picos a common way to receive and run transmissions. Each
transmitter receives the complete transmission in advance and handles its
own timing; individual symbols do not depend on USB or network traffic.

Keep WSPR running on the controller, schedule another band on a second Pi,
and send QRSS from a Pico—all from the same web interface.

## Precompiled binaries are back

We once again supply compiled WsprryPi binaries for Raspberry Pi OS, formerly Raspbian, supporting stable (Trixie) and oldstable (Bookworm) on supported 32-bit and 64-bit installations. The current Beta installer automatically selects the matching binary, avoiding application compilation on the Pi and saving up to an hour on older hardware such as the Pi 1 and Pi Zero.

## Fleet control

- **Find and name your transmitters.** Discover USB Picos and nearby network
  devices, or add a network address manually. Save devices for later use.
- **Give each output its own schedule.** Run WSPR, QRSS, FSKCW, DFCW or timed
  test tones where the selected transmitter supports them. Fleet WSPR schedules
  send one frame at a time.
- **Manage outputs independently.** Pause, stop or edit one output without
  replacing the other schedules. A failed connection pauses the affected
  schedule; check its status before resuming. Missed transmissions are not
  automatically replayed.
- **Take control at the remote Pi.** Its operator can end remote work immediately
  or let the current transmission finish before returning to local operation.
  Taking local control cancels that output's future remote schedule.

Picos connect over USB or a supported network connection. Remote Pis can use
their GPIO output or a Si5351. Adding a device or saving settings does not
start transmission. Remote operation currently requires an explicit
experimental setting; the setup guide explains how to enable it.

**Plain LAN** connections to Pis or Picos are unencrypted. Use them only on
a network whose users you trust to control the transmitters. Losing a
connection does not confirm that a transmitter has stopped.

## Set up and maintain Picos from the Pi

- **Manage station and device settings.** Edit callsign, locator, reported power,
  Wi-Fi, device name and supported hardware settings from Fleet. Compatible
  firmware supports compound callsigns and extended locators through WSPR
  Type 2 and Type 3 messages.
- **Save setup progress.** Save valid station fields while finishing the rest
  later. Invalid entries stay visible for correction. Applying saved station
  settings is a separate action from saving them or enabling transmission.
- **Set GPIO drive strength.** Choose from the Pico's supported drive settings
  and restart it explicitly to apply a change. Drive strength and reported WSPR
  power are separate settings.
- **Update firmware over USB.** Check an image before installing it, follow the
  on-screen instructions for older firmware, and resume or recover an
  interrupted update. Firmware maintenance blocks conflicting changes.

Full flash erase is a separate action that removes firmware and saved data,
creates no new backup, and leaves the Pico ready for firmware installation.
Pico features depend on the installed firmware; older versions may offer fewer
controls. Firmware installation and erase require USB.

## Other improvements for your station

- **Pi 5-family GPIO transmission.** Support includes Pi 5/CM5 GPIO output using
  the separate RP1 driver, with GPIO4/GPIO20 selection and recovery controls.
  Installing the driver or choosing an output pin does not start transmission.
- **Regional and custom WSPR frequencies.** Choose Default, Preset or Custom
  dial frequencies by band, including the legacy and WRC-15 choices for 60 m.
  The settings show the resulting transmit frequency and preserve custom values.
- **Better frequency calibration.** GPIO correction can combine the system-clock
  estimate with a measured radio-frequency correction. Si5351 has its own PPM,
  reference-clock and crystal-load settings. Clock synchronization alone does
  not calibrate the transmitted frequency.
- **More useful Test Tone controls.** Choose a band or enter an exact RF
  frequency. The previous operating mode is restored afterward, and the old
  GPIO tone-frequency offset is corrected. For remote transmitters, use Fleet's
  timed tones.
- **More flexible filter switching.** Bands can share a selector pin when their
  switching polarity agrees. GPIO26/27 are available, and GPIO4/20 choices
  account for the selected RF output.
- **Clearer feedback and steadier browser use.** Pending edits are no longer
  reported as saved, frequency controls work better on small screens, and
  browser and log-viewer cleanup reduces resource buildup during repeated
  visits. Spots offers both WSPR and QRSS.
- **Support bundles from the browser.** Collect, review and download diagnostics
  without using a shell. Sending an encrypted copy for private support requires
  separate consent; creating a bundle does not upload it.
- **Local-network operation without Internet.** Use the web interface on an
  isolated physical LAN. Downloads and online support still need Internet
  access, and scheduled transmissions still need a suitable clock.
- **PHP maintenance audit.** A separate command-line tool reports PHP package and configuration findings with upgrade guidance. It does not run automatically during installation. See the [audit instructions](https://github.com/WsprryPi/WsprryPi/blob/devel/scripts/README.md#php2shell-configuration-audit-and-partial-mitigations).

## Before upgrading

1. **Back up your station.** Keep your configuration, executable, local web
   customizations and Pico recovery files. Stop scheduled transmissions and
   finish any interrupted Pico firmware work first.
2. **Choose the right installation.** Use the current Beta installer command below. It downloads the newest published executable for `devel` that matches your Pi's OS release and 32-bit or 64-bit userspace, skipping application compilation, application build dependencies and application swap preparation. If no compatible executable is published, it builds from source; a lookup, download or validation failure stops installation. Pi 5 GPIO driver preparation can still require compilation. See the [current Beta installation procedure](https://wsprry-pi.readthedocs.io/en/devel/Install/beta1.html) for options. The default stable-channel installer remains separate.
3. **Check calibration after migration.** Review the migration guidance before
   reusing previously measured GPIO correction values. Scripts using the old
   `--use-ntp` option must use `--use-system-clock-frequency-estimate` instead.
4. **Review network control.** The Pi's inbound Plain LAN transmitter control
   is enabled by default. Turn off **WTP Server** if you do not want remote
   control. Browser controls are restricted to directly connected networks;
   remote access through a proxy may need review.
5. **Supporting tools are included.** The current Beta installer supplies Python and downloads the matching prebuilt USB-capable picotool package for Pico firmware maintenance. It keeps an already compatible picotool installation. On Pi 5-family systems it also installs the RP1 GPIO driver, matching kernel headers and required build tools. No separate picotool or RP1 driver installation is needed, and picotool is never compiled on the Pi.

Install or update the current Beta with:

```sh
curl -fsSL https://raw.githubusercontent.com/WsprryPi/WsprryPi/refs/heads/devel/scripts/install.sh | sudo REPO_BRANCH=devel bash
```

This command follows current `devel` for the installer, web interface and supporting files, which can be newer than the selected release executable. The published Beta 1 executable still reports `4.0.0-beta.1+1e047a4`. The installer in the frozen Beta source tag still defaults to compilation; use the command above for automatic binary downloads.

Published Beta 1 installation guidance:

- [Installing WsprryPi — Pico USB firmware tools](https://wsprry-pi.readthedocs.io/v4.0.0-beta.1/Install/index.html#pico-usb-firmware-tools)
- [Install 4.0 Beta 1 — Pico USB firmware tools](https://wsprry-pi.readthedocs.io/v4.0.0-beta.1/Install/beta1.html#pico-usb-firmware-tools)

Available bands and modes depend on the selected hardware. A listed band is
not a promise that every transmitter supports it, and local operating rules
still apply. Reverting to an older executable alone does not restore older
settings, drivers or Pico firmware; keep a complete recovery set.

Pi 5 route evidence is bundled with the application and checked locally; no
separate qualification-release download or cache refresh is required. Evidence
availability does not grant transmission permission.

The four executables were built from
[`1e047a44`](https://github.com/WsprryPi/WsprryPi/tree/1e047a44a44f07d2eb52dfd3c3537d2d24e60143).
The [Beta source tag](https://github.com/WsprryPi/WsprryPi/tree/v4.0.0-beta.1)
also contains accepted installer/helper repairs. The
[publication manifest](https://github.com/WsprryPi/WsprryPi/releases/download/v4.0.0-beta.1/publication-manifest.json)
and [checksums](https://github.com/WsprryPi/WsprryPi/releases/download/v4.0.0-beta.1/SHA256SUMS)
bind that mapping and all four raw executable downloads.

The current `devel` installer verifies an automatically selected download against its published manifest or GitHub asset SHA-256 checksum when supplied; Beta 1 provides these checksums. Explicit `--binary-source release --release-tag ...` downloads do not automatically acquire an expected checksum, and the frozen Beta helper does not compare checksums. Verify explicit downloads independently against the release's `SHA256SUMS` before installing them with `--binary-source local`. Architecture, runtime-library and version checks are separate from checksum verification.

Fresh clean installation, physical acceptance of three of the four exports,
reboot, fresh GPIO4 selection and rollback rehearsal remain unperformed Beta
checks. Changed supporting helpers have isolated software/CI acceptance with
historical target evidence reused; fresh target installation/status of those
changed files was not performed. Runtime evidence does not qualify every
hardware configuration or RF path. Intermittent Si5351 startup-readiness failures
observed on one system remain unexplained; inspect readiness before operation.

See the [versioned operator manual](https://wsprry-pi.readthedocs.io/en/v4.0.0-beta.1/) for setup
and use. Engineering details, compatibility limits and release-verification
records are kept in the
[evidence ledger](https://github.com/WsprryPi/WsprryPi/blob/v4.0.0-beta.1/release_tools/4.0-Beta-1-Release-Evidence.md).

## Set up and maintain Picos from the Pi

- **Manage station and device settings.** Edit callsign, locator, reported power, Wi-Fi, device name and supported hardware settings from Fleet. Compatible firmware supports compound callsigns and extended locators through WSPR Type 2 and Type 3 messages.
- **Save setup progress.** Save valid station fields while finishing the rest later. Invalid entries stay visible for correction. Applying saved station settings is a separate action from saving them or enabling transmission.
- **Set GPIO drive strength.** Choose from the Pico's supported drive settings and restart it explicitly to apply a change. Drive strength and reported WSPR power are separate settings.
- **Update firmware over USB.** Check an image before installing it, follow the on-screen instructions for older firmware, and resume or recover an interrupted update. Firmware maintenance blocks conflicting changes.

Full flash erase is a separate action that removes firmware and saved data, creates no new backup, and leaves the Pico ready for firmware installation. Pico features depend on the installed firmware; older versions may offer fewer controls. Firmware installation and erase require USB.

## Other improvements for your station

- **Pi 5-family GPIO transmission.** Support includes Pi 5/CM5 GPIO output using the separate RP1 driver, with GPIO4/GPIO20 selection and recovery controls. Installing the driver or choosing an output pin does not start transmission.
- **Regional and custom WSPR frequencies.** Choose Default, Preset or Custom dial frequencies by band, including the legacy and WRC-15 choices for 60 m. The settings show the resulting transmit frequency and preserve custom values.
- **Better frequency calibration.** GPIO correction can combine the system-clock estimate with a measured radio-frequency correction. Si5351 has its own PPM, reference-clock and crystal-load settings. Clock synchronization alone does not calibrate the transmitted frequency.
- **More useful Test Tone controls.** Choose a band or enter an exact RF frequency. The previous operating mode is restored afterward, and the old GPIO tone-frequency offset is corrected. For remote transmitters, use Fleet's timed tones.
- **More flexible filter switching.** Bands can share a selector pin when their switching polarity agrees. GPIO26/27 are available, and GPIO4/20 choices account for the selected RF output.
- **Clearer feedback and steadier browser use.** Pending edits are no longer reported as saved, frequency controls work better on small screens, and browser and log-viewer cleanup reduces resource buildup during repeated visits. Spots offers both WSPR and QRSS.
- **Support bundles from the browser.** Collect, review and download diagnostics without using a shell. Sending an encrypted copy for private support requires separate consent; creating a bundle does not upload it.
- **Local-network operation without Internet.** Use the web interface on an isolated physical LAN. Downloads and online support still need Internet access, and scheduled transmissions still need a suitable clock.
- **PHP maintenance audit.** A separate command-line tool reports PHP package and configuration findings with upgrade guidance. It does not run automatically during installation. See the [audit instructions](https://github.com/WsprryPi/WsprryPi/blob/devel/scripts/README.md#php2shell-configuration-audit-and-partial-mitigations).

### WTP/1, Fleet and network control

WTP/1 is the device-neutral finite-job protocol. Complete `rf-events/1` jobs
are loaded before ARM; the member's local clock/engine owns event timing.
WTP/1 does not define stored schedules, station/hardware configuration,
provisioning, browser APIs, firmware maintenance or RF filtering. Separately
versioned management resources cover those functions.

The controller can run zero through eight remote assignments alongside its
local schedule. Each assignment has an independent mode, RF base frequency,
repeat period and UTC phase. Fleet WSPR assignments are single-frame jobs;
selected-Pico Type 2/3 station planning is not a promise that the assignment
editor supports every extended WSPR plan. Native Pi members use their selected
GPIO, RP1 GPCLK or Si5351 backend. Current CAPS and host frequency/route policy
must accept each job.

Remote dispatch requires `--allow-unqualified-frequency` or
`[Experimental] Allow Unqualified Frequency = true` on the controller.
Outside-amateur-band requests require the separate existing opt-in. RP1 retains
its exact-operation host confirmation. Saved profiles, discovery and successful
capability inspection grant none of those overrides.

Profiles retain explicit device identity and connection settings. DNS-SD
observation is link-local and not authentication; routed/VLAN deployments need
manual endpoints. USB, Plain LAN and authenticated Pico TLS share WTP/1 job
semantics, without automatic transport downgrade or endpoint retargeting.
The Pi listener provides Plain LAN, not TLS; Plain LAN does not authenticate
individual users or encrypt traffic. Browser network-location guards are
separate from transport authentication.

Failed/uncertain assignments pause independently, consumed slots are not
replayed, and successful reconciliation leaves the assignment paused. A lost
connection, expired result or changed boot is not output-off evidence. Local
Pi takeover revokes future remote assignments through durable takeover history;
the controller has no veto. Unconfirmed output-off blocks reuse.

### Pico management and firmware compatibility

Configuration saves negotiate supported preservation/update capabilities rather
than erasing fields an older controller does not understand. Stale, ambiguous
or unsupported replies preserve drafts and require explicit readback/review;
a mutation is not automatically replayed. The Pi station editor consumes
`transmitter-progress/1`; newer amplifier-aware progress views can be refused
and require the corresponding Pico controls. Consumer profile-owned application
remains in Pico transactional setup. Complete atomic APIs and old-firmware
complete-save behavior retain their own supported scope. Test reference commits
are not firmware-image pins or acceptance of every later firmware combination.

Pico drive supports nominal 2/4/8/12 mA only with the advertised descriptor.
Saved value, active-at-boot selection and pad readback are distinct; 4 mA is the
Pico default. Drive is separate from reported WSPR dBm and measured RF power.
Host USB UTC delivery requires qualified clock observations. New WTP settings
use 100,000,000 ns (100 ms) maximum admitted uncertainty; explicit existing
limits, including 1 ms, are not silently increased. UTC synchronization does
not calibrate RF frequency.

The USB firmware selector defaults to Pico `main` independently of the Pi
branch. Missing images are refused without substitution. Compatible installer
updates are independent of Pi releases; active recovery keeps its original
verified installer snapshot. BOOTSEL handoff, exact-device identity, retained
maintenance holds, backup and continuation are governed by the installer
contract. Full erase verifies all 4 MiB blank, removes persistent flash data,
creates no new backup and leaves BOOTSEL; ROM/OTP/immutable identity are not
flash erase targets. Unresolved maintenance is not bypassed by deleting markers
or downgrading. Draft and credential formats can survive firmware downgrade.

USB maintenance requires Python 3.10+ and USB-enabled picotool >=2.3 within 2.x. The original tagged Beta 1 supporting source did not install picotool or the Pico SDK. The [October 22 supporting-tools update](#october-22-prebuilt-picotool-supporting-tools) adds prebuilt picotool packages through the current devel installer. Management carriers, resource revisions and permission boundaries remain in the engineering guides.

### Platform, installation and maintenance details

The binary matrix is ARMv6 hard-float/AArch64 × Bookworm/Trixie userspace.
Bullseye and a separate ARMv7 export are outside it. Local precompiled mode
validates ELF architecture/ABI, loader, library/symbol resolution and version
before replacement; it skips application compilation/swap preparation, not
runtime packages, supporting files or optional RP1 module prerequisites.
RP1 needs compatible kernel headers and DKMS/build tools. Source preflight
separates RAM, zram and independently backed swap; temporary build swap is
installer-owned and cleaned up without replacing existing swap.

The installer preserves current persistent WTP keys, custom uncertainty,
WSPR profile/preferences and supported selector keys, and performs the supported
legacy GPIO migration before stock defaults can hide absent canonical values.
Failed/empty merge stops publication. Supported service-mask recovery,
noninteractive logging, ownership-aware provider removal and idle route/reboot
restoration have the exact source/test/target dispositions recorded above.
Installing or selecting an RP1 route never grants RF permission.

Update detection requires eligible release or positive ancestry evidence.
Packaged UI identity, installed UI classification and running-service identity
are independent. Modified UI backup, cache refresh convergence, real version
metadata and the WSPR encoder's stale-callsign repair retain their existing
source evidence. Missing/malformed Pi revision data fails closed rather than
fabricating BCM2835 identity. Components are ordinary tracked parent content;
there is no separate component-pull update procedure.

The directly connected physical-LAN browser guard does not require an Internet
route; it does not add individual authentication or encryption. Discovery needs
Avahi support. The managed inbound Plain LAN server defaults on after confirmed
startup quiescence, port 31417, with physical-interface selection. Support
collection remains local unless consented intake is invoked; the reviewed bytes
are encrypted under signed destination policy, and opening the upload service
is not confirmed delivery.

### Adversarial finding, repair and contract checks

**P2 — physical endpoint profiles could pass Pi planning and fail the published
provider.** The numerical planner deliberately supports exact divider words
and counts that round to zero. The physical event compiler copied those into a
UAPI requiring adjacent words, both counts positive and one shared integer field.
The frozen candidate reproduces this production defect. At 14,097,100 Hz with
caller correction 46.369969482318 ppm, it produces words 929779/929780 and
counts 0/66792; the real published C core returns `INVALID`. This is a consumer
translation defect, not a reason to modify or republish the provider.

The repair leaves the numerical planner untouched and preserves already valid
profiles exactly. Endpoint cases use adjacent same-integer Q16 words with
positive counts and the original 66,792-entry weighting period. Their mean is
recomputed and must meet the existing 0.01 Hz tolerance before acquisition.
Reported realized frequencies describe the submitted profile. The repaired
20 m example uses 1/66791, is accepted by the real provider core and has
independently calculated error +0.000226999865 Hz. A 30-case real compiler/core
comparison reproduced five Pi-admitted/provider-rejected cases before the fix
and zero afterward. A near-100 MHz case whose forced positive count would
exceed tolerance is rejected, preserving fail-closed admission.

New backend regressions cover exact/near endpoints on both routes and all five
supported modes, independently calculated means, realized reporting, maximum
Q16, count/overflow/mixed-integer refusals, integer-transition refusal and
unrepresentable physical tolerance. Physical validation now matches the provider
tone/resource restrictions, including RF-off tone indices. Independent review
caught possible interior count drift from floating-point recomputation; the
final repair explicitly preserves valid numerical profiles. Test failure/index
guards and the meaningful tolerance-refusal case were added before reassessment.
Fresh independent source reassessment found no remaining actionable finding.

The audited path is request/ExecutionPlanCompiler → physical event compiler →
backend → Linux adapter/UAPI → published core/resource/execution logic. Physical
